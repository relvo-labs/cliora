## 2. `AR-10` — Agents 頁（`/agents`）

一個清單，欄位對應 `research/02/09` §4.3b（該節已於 2026-08-10 更新）：

| 欄 | 來源 | 注意 |
|---|---|---|
| 名稱 | `agent_runners.name` | |
| 所在 node | join `nodes` | **連到既有的 node 詳情頁**，不重做一個 |
| 線上狀態 | `registry.is_connected(node_id)` 現算 | **就是 node 的線上狀態**（D16），不另做指示燈 |
| runtimes | `agent_runners.runtimes` | 空陣列時顯示原因（`04-…md` §5.3） |
| labels | `agent_runners.labels` | 🆕 **顯示但不比對**（裁決：label match 是後續功能）。欄位旁註明「目前僅供辨識」 |
| 並行度／目前負載 | `max_concurrent` ＋ 進行中的 run 數 | 等回覆的 run 另計（`02-…md` §2.1） |
| 🆕 **磁碟／配額用量** | heartbeat 回報 | 用盡時顯示原因，**不是顯示成離線**（`04b-…md` §4.1） |
| 🆕 **用途姿態** | `agent_runners.dedicated` | `✔ 專用 runner（此 node 未設定任何 allowed root）` 或 **`⚠ 混合用途（此 node 也提供互動式 Session；Agent 可讀取那些目錄）`**。見下 |
| 啟用開關 | `enabled` | `agent.manage` 才能動 |

三個規劃點名、實作最容易漏的：

- **容量或磁碟用盡時顯示原因，不是顯示成離線。** 「滿載」「磁碟用盡」「離線」是三件事，
  而 runner 在前兩種情況下都不 poll（`04-…md` §3.1），從 Central 看不出差別——
  所以那一欄要顯示 `3/3（滿載）` 或 `磁碟用盡（4.8 / 5.0 GB）`，
  而不是讓線上燈變色。**三種狀態三種文案**，各有一條測試。
- **每個 runner 顯示「目前被指定的卡片數」**，讓人看得出某台機器是不是被綁死了。
  這是一條 `COUNT(*) FROM tasks WHERE assigned_runner_id = ?` 的查詢，
  跟著清單一起回，不是第二次往返。
- **舊 daemon 的那一列**：`nodes.agent_runner = false` 時顯示
  「此 node 的 agentd 需升級到 0.9.0」，**不隱藏那台 node**
  ——隱藏會讓人以為機器不存在（與 §3.2 的 picker 同一條理由）。

### 2.0 🆕 「用途姿態」那一欄為什麼要醒目

**這是本頁唯一一個承載安全語意的欄位**（`04b-…md` §3.4／§2.5）。
「Agent 讀不到使用者的 workspace」這件事**平台沒有技術上的隔離**——
run 的子程序與 agentd 同一個 OS 使用者，而 allowed roots 必須被那個使用者讀寫。
只有在 `allowed_roots` 為空的 node 上，它才是恆真的。

所以 ⚠ 那一格的文案要說出**後果**而不是狀態：

> ⚠ 混合用途：此 node 也提供互動式 Session。
> 在這台機器上執行的 Agent **可以讀取那些 Session 的工作目錄**。
> 要讓它讀不到，把這台 node 的 `allowed_roots` 清空（成為專用 runner），
> 或用另一台機器跑 runner。

**不是紅色的錯誤，是琥珀色的資訊** ——混合用途是一個合理的選擇
（一個人的單台開發 VM），而這一格的工作是讓那個選擇**是被看見的**，
不是讓它看起來像壞了。

### 2.1 🆕 沒有綁定 UI，但要有一行姿態宣告

裁決之後本期**沒有** `project_agents`，所以 Agents 頁上沒有綁定的欄位、
沒有勾選框、也沒有「綁定＝授權取用機密」那句警告（那些是 V2.3 的）。

**取而代之要有一行，而且不能是小字**：

> 任何 runner 都可以領取任何專案的卡片，也會拉取該專案的程式碼。
> 授權邊界是 **enrollment**——只有 Admin 能讓一台機器加入。
> 逐專案的授權從 V2.3 起提供。

這一行是本期最容易被當成 bug 回報的東西（「為什麼我找不到綁定設定」），
所以它要出現在**三個**地方（`02-…md` §6）：`rbac.py` 的註解、ADR 0029、以及這裡。

### 2.2 🆕 Project Settings → Repository

Agent 要自己 clone，平台就得知道 repo 在哪（`06-…md` §2.3）。

- 表單是**三個欄位**（scheme／host／path）＋ default branch，**不是一個 URL 輸入框**。
  這在 UI 上看起來比較囉嗦，而那是刻意的：一個 URL 輸入框會在第一天就收到
  `https://user:token@github.com/…`。表單旁邊一句話說明為什麼拆開。
- **明示本期不管理憑證**：

  > clone 使用該 node 上既有的 git 認證（ssh-agent、credential helper、或公開 repo）。
  > 平台在這一版不管理 git 憑證；私有 repo 只有在該機器本來就拉得動時才拉得動。
  > 平台管理的憑證從 V2.3 起提供。

- host 不在部署 allowlist 內時**即時提示**（不是等送出才 400），
  並列出目前允許的 host——那是一個 Admin 要改環境變數的事，使用者需要知道要去問誰。

## 3. `AR-10` — 卡片上的「派給 Agent」

### 3.1 入口

Task Detail 的執行區，V2.1 那裡目前寫「本階段由人執行」（`plan/17` D11 的文案），
本期換成兩個按鈕：**「派給 Agent」** 與既有的 **「我自己來」**（開互動 Session）。
兩者並存、不互相取代（D26）。

🆕 **裁決刪掉了原本要寫在這裡的那句警告。** 原本是：

> ~~此 run 會直接在 `<workspace_path>` 上執行，不是隔離目錄。V2.3 起改為隔離環境。~~

現在 run 拉的是自己的一份 clone，使用者的 workspace 不被碰。
**取而代之要顯示的是它會拉什麼**：

> 這個 Agent 會把 `github.com/Lei-k/Traqora`（`main`）拉到它自己的隔離目錄執行。
> **你的工作目錄不會被修改。**
> 平台會把成果以卡片產物的形式帶回這裡——**這一版平台不會替你建立分支或 PR**。

第二句回答「它會不會弄壞我的東西」，第三句回答「做完之後我要去哪裡看」。
第三句的措辭要精確：**主詞是「平台」**。Agent 自己可以用那台機器的 git 憑證推分支
（第二次裁決允許），而平台不保證、不記錄、也不攔——
所以文案不能寫成「不會有分支」，那會變成一句不真的話。
若 run 摘要顯示有未推送的 commit 為 0（`04b-…md` §5.4），Run 詳情頁會提示
「這個 run 可能已把 commit 推到遠端」，讓人自己去看。

### 3.2 Agent picker

預設是 **「任一符合資格的 Agent」**（`assigned_runner_id = null`）。
可改為指定某一個。🆕 **picker 列出所有 runner**——裁決之後沒有綁定，
所以沒有「該 Project 的 runner」這個子集合。每一列顯示名稱、node、目前負載、線上狀態。

**不符資格的顯示為停用並附原因，不是隱藏。**
隱藏會讓人以為那台機器不存在。原因用 `03-…md` §4 的 409 碼翻成人話：

```text
dev-vm-01   3/3 滿載          可選（會排隊）
build-02    離線              可選（會排隊，卡片會顯示「等待指定的 Agent」）
gpu-01      磁碟用盡           可選（會排隊）← 它會自己恢復，所以不是「停用」
old-vm      runtime 不符       停用
mac-01      已停用             停用 ← 連到 Agents 頁（啟用是 Admin 的權力）
```

🆕 **`未綁定此專案` 與 `缺少 label` 兩列消失了**（裁決）。它們會在 V2.3 回來，
而 picker 的三種狀態（可選／可選但會等／停用）的分類邏輯**不變**——
這是把 `03-…md` §4 的檢查順序原封不動搬到 UI 上的結果。

**「滿載」與「離線」是可選的，「不符資格」是停用的**——這正是 D17b 邊界 2
的兩種失敗在 UI 上的形式。它們的差別在 picker 上就要看得出來，
而不是等按下去之後靠 409 或 202 告訴你。

### 3.3 看板卡片上的 run 狀態

看板一次要顯示幾十張卡，所以徽章的資料要跟著 board 查詢一起回，不是每張卡一次往返。
`GET /api/projects/{id}/board` 的每張卡多三個欄位：
`active_run_status`、`active_run_runner_name`、`waiting_reason`。

| 狀態 | 徽章 |
|---|---|
| `queued`（未指定） | 排隊中 |
| `queued`（指定，離線） | **等待指定的 Agent：dev-vm-01（目前離線）** |
| `queued`（無符合資格者） | **等待可用的 Agent** |
| `claimed`／`running` | 執行中 · dev-vm-01 |
| `waiting_for_input` | **等待你的回覆**（醒目樣式） |
| 最近一次 `failed`／`lost` 用盡 | 失敗（連到 Run 詳情） |

第二列與第三列的文案**逐字不同**（出口條件 4／5），
而且它們是同一個 `waiting_reason` 欄位的兩個值——前端不重算，
因為那個判斷要跑資格查詢（`06-…md` §2.2）。

**M1 的教訓要用上**（`plan/17/09` §3 第 1 條）：board 的回應大小是決定形狀的東西。
這三個欄位每張卡約 80 bytes，200 張卡是 16 KB——可接受，但要在 `AR-10` 量一次
並記進 `10-…md`，不是假設。

## 4. `AR-11` — Run 詳情頁（`/projects/:id/runs/:runId`）

- 狀態、所屬 Task 與 Project、執行的 runner、**attempt 次數與這是第幾次 run**
  （`seq`／`attempt` 兩個數字都要，它們不是同一件事）。
- 🆕 **來源**：clone 的 repo（`host/path`）、`source_ref`、**`commit_sha`**（可複製）。
  這一行回答的是「這次跑的是哪一版程式碼」，而它是 Run 詳情頁最常被問的一件事。
- 🆕 **run 目錄大小**（`disk_bytes`）與清理時間。
  **不顯示 run 目錄的路徑**：那是 daemon 的內部狀態，顯示它只會讓人想去 ssh 進去看，
  而那個目錄的存在期限是 3 天。要看內容就看產物。
- 時間軸：`queued → claimed → **checked_out** → running → …`，**每一段的耗時**。
  🆕 `checked_out` 是裁決帶來的一段，而它值得單獨一格：clone 一個大 repo 可能佔掉
  整個 run 的一半時間（M11），而使用者需要分得出「卡在拉程式碼」與「卡在執行」。
- 🆕 **「最後動靜」**：`task_runs.last_event_at` 顯示成「最後動靜：3 分鐘前」。
  **這一行是 D21 在 UI 上的形式**——它回答使用者真正在問的問題
  （「它是卡住了還是還在做？」），而那個問題原本只有一個 6 小時後才會有的答案。
- **Log 檢視**：`?after_seq=` 每 2 秒輪詢（`06-…md` §2.1 選分頁不選串流）；
  可跟隨（自動捲到底）、可搜尋（前端在已載入的內容裡找）、
  **明示截斷位元組數**、**明示保留期到期時間**。
  🆕 **內容是 JSONL 事件不是純文字**：每一行渲染成「事件型別 ＋ 摘要」，
  原始 JSON 收在可展開處。**不是把 JSON 直接倒在畫面上**——那比純文字更難讀。
- 取消按鈕（`run.cancel`），需 `run.cancel` 動作；沒有該動作時按鈕不出現。

四個實作注意：

1. **「明示截斷」要顯示在截斷發生的位置**，不是只在頁首寫一行。
   `run_logs` 有 `truncated=true` 的標記列（`03-…md` §7），
   那一列渲染成一條分隔線 ＋「已省略 N 位元組」。
2. **保留期到期時間**來自 `task_runs.logs_expire_at`，顯示成本地時間。
   到期之後這一頁的 log 區顯示「這次 run 的 log 已於 <時間> 依保留期刪除」——
   **不是空白**。空白會讓人以為系統壞了。
3. **不做 xterm.js。** run log 是 JSONL 事件流，不是終端——
   🆕 **D21 之後這一條變得更明確**：輸出裡沒有 ANSI，因為我們刻意不走 PTY。
   一個事件列表元件，不引入 `frontend/src/terminal` 的任何東西
   （那是 `GATE-AR-TOUCH-LIST` 的禁區）。
4. **輪詢在頁面不可見時停止**（`document.hidden`），否則一個開著的分頁會
   對一個已經結束的 run 永遠每 2 秒打一次。

## 5. `AR-11` — 卡片訊息串

這是「平台作為橋樑」最直接的體現，要做得好用而不是做成一個註解欄位。

- **三種來源混排、可辨識**：使用者用一般樣式、Agent 用帶 runtime 圖示的樣式、
  系統事件用低調的單行樣式。
- **Agent 的問題要醒目**，並在**卡片頂部**與**看板上**同步顯示「等待你的回覆」。
- **輸入框固定在下方**，送出後即時出現。
- 🆕 **沒有 `task.update` 的人（Viewer）看得到訊息串，但沒有輸入框**（2026-08-11 裁決）。
  **這一格要處理一個尷尬的狀態**：一張卡在等 Agent 的問題被回覆，
  而看到它的人沒有權限回。所以 Viewer 看到的是
  「等待回覆（你沒有回覆這張卡的權限）」而不是一個按不下去的送出鈕
  ——**說出原因，而不是給一個壞掉的控制項**。
- **一行說明**：「Agent 會在下一次拉取時看到你的回覆」——
  不要讓人以為 Agent 沒回應（D24：不做中斷式推送）。
- **顯示「Agent 上次拉取訊息：<時間>」**。這一行讓等待變得可理解，
  資料來源是 `run_tokens.last_used_at`（那個「best-effort、不在關鍵路徑上」的欄位
  在這裡終於有了讀者）。

## 6. `AR-11` — 產物區

卡片上**獨立一區**，與訊息串並列：

- 列出所有產物：檔名、大小、來自哪次 run、時間、上傳者（**人或 agent 要分得出來**）。
- 訊息裡的附件**同時**出現在訊息與產物區——同一件東西兩個入口，不是兩份資料
  （`task_artifacts.message_id` 是那個關聯）。
- 圖片顯示縮圖（走 `/preview`），其餘一律**下載按鈕**。
- 🆕 **附加產物需要 `task.update`**（同上）。Viewer 看得到、下載得到，但沒有附加入口。
- **不做「在新分頁開啟」。** 那等同內嵌渲染，而 Cliora 是單一 origin 部署
  （`00-…md` D14）。這一條要寫進元件的註解，否則下一個人會覺得少了一個明顯的功能。
- 專案配額用量顯示在 Project Settings；接近上限（>80%）時在卡片上提示。
- 被刪除的產物顯示為一行灰字（檔名、大小、刪除者、理由），不是消失（`06-…md` §6）。

**不要在 UI 上暗示產物是安全的**（D29 §5）。產物區的說明文字：

> 產物是 Agent 產生的檔案。平台不檢查內容，也不保證它不含機密。

這句話要在，而且不要寫成一個要點開才看得到的 tooltip。

- **`v-html` 全域掃描**：`frontend/src/` 裡新增的檔案不得出現 `v-html`。

  所以要把它變成一條 gate 而不是一個習慣。
