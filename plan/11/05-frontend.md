# 05 — 前端（PG-10、PG-11、PG-12）

> 需求變更（2026-08-01）：新增 `PG-10`（系統整合設定頁）；原本的「Node 詳情 Tunnels 區塊」升級為
> `PG-11`（**每個 node 的埠轉發設定頁**，含該節點的允許範圍與上限設定）。

## PG-10：系統整合設定頁

### 1.1 路由與導覽

| 項目 | 決定 |
|---|---|
| 路由 | `/settings/integrations`（新增），元件 `views/IntegrationsView.vue` |
| 導覽入口 | `AppLayout.vue` 的 sidebar 新增一項「整合設定」，**僅在持有 `integration.manage` 時顯示** |
| 為什麼是獨立頁而非 Dashboard 上的一塊 | 它是平台級設定，且未來會有第二個整合項。**頁面以「整合清單」的形式呈現（目前只有一列：Pinggy 埠轉發）**，這樣加第二個整合時不必重排版面 —— 但**不建抽象化的整合框架**，第二個來了再說 |
| 沒有 `integration.manage` 時直接進網址 | 顯示伺服器回的 403 狀態（沿用 `AuditView.vue` 的既有做法：不做前端 guard，因為前端 guard 只決定顯示，不決定授權） |

### 1.2 頁面內容（五塊，順序即使用順序）

| # | 區塊 | 內容 |
|---|---|---|
| 1 | **狀態** | 啟用／停用開關；目前狀態徽章；`active_tunnel_count`；`secret_key_available` 為假時**取代整個表單**顯示「此環境未設定憑證加密金鑰，因此無法保存服務商憑證」＋要給部署管理員看的一句話（設 `CLIORA_SECRET_ENCRYPTION_KEY`） |
| 2 | **憑證** | 「已設定 · 指紋 `ab12cd34` · 由 alice 於 3 天前更新」或「尚未設定」；輸入框（`type="password"`、`autocomplete="off"`）＋儲存／清除。**永遠不顯示 token 的任何字元**，也不做「顯示密碼」的眼睛圖示 —— 沒有東西可顯示，因為前端從未收到它 |
| 3 | **方案** | `free` / `pro` 二選一，旁邊一句話說明差異（免費：60 分鐘、網址會變；Pro：固定子網域、無時限）。選 `pro` 但憑證未設定 → 就地提示，不讓他儲存一個必然失敗的組合 |
| 4 | **預設值** | **併發預算**（1–100，預設 **8**；標明這是**整個平台同時存活的隧道數**、旁邊即時顯示「目前 3／8」、說明「請依你的方案填寫；超出方案會讓新隧道踢掉舊的」）、預設保護模式、預設 TTL、全域 port 上限。**每台 node 的上限不在這裡**，在各 node 的埠轉發頁（`PG-11`） |
| 5 | **啟用前的確認**（D14 第一處） | 首次啟用時必須勾選的四句話：流量會經由 Pinggy 轉送／**對方可見未加密的 HTTP 內容**／因此僅適合預覽開發中的應用／訂閱與帳號由你自己持有。勾選後才能按啟用；`acknowledged_at` 已存在則不再顯示 |

### 1.3 停用的兩段式處理

停用只擋新建，既有隧道不會被關（`04-…md` §0.2）。UI 必須誠實：

- 按下停用時，若 `active_tunnel_count > 0`，確認對話框寫「將停止建立新隧道；目前 N 條既有隧道會繼續執行至到期」。
- 停用後，狀態區塊顯示那 N 條的連結與一個獨立的「一併關閉全部」按鈕（逐條呼叫 `DELETE /api/tunnels/{id}`，**逐條回報成功與失敗**，離線 node 上的隧道會失敗，這是預期的）。

把「擋住新的」與「收掉舊的」分成兩個動作，是因為第二件事可能部分失敗，而一個可能部分失敗的開關不該偽裝成一個開關。

### 1.4 驗收

- 單元測試：`secret_key_available=false` 時表單被取代、憑證區塊只顯示指紋（**斷言 DOM 中不存在任何 token 字元**）、`pro` + 無憑證的阻擋、首次啟用的確認流程、`acknowledged_at` 已存在時不再要求、停用確認文案含既有隧道條數。
- 授權：無 `integration.manage` 時 sidebar 不顯示入口，且直接進網址顯示 403 狀態。

## PG-11：每個 node 的埠轉發設定頁

### 2.1 路由與進入點

| 項目 | 決定 |
|---|---|
| 路由 | `/nodes/:id/tunnels`（新增），元件 `views/NodeTunnelsView.vue` |
| 進入點 | Node 詳情頁（`NodeDetailView.vue`）新增一個「埠轉發」區塊，內含摘要（目前幾條、狀態）與「管理」連結；**完整設定與清單在獨立頁** |
| 為什麼是獨立頁 | 需求原話是「每個 node 應該要有針對 pinggy 的設定頁面」。而且 Node 詳情頁已有六個區塊（`:221`、`:259`、`:275`、`:288`、`:324`、`:414`），再塞一個「設定＋清單＋建立表單」會讓那一頁變成兩件事 |
| 整合未啟用時 | 摘要區塊與路由都顯示「埠轉發整合尚未啟用」＋（若持有 `integration.manage`）到 `/settings/integrations` 的連結。**不隱藏**：使用者需要知道為什麼沒有這個功能 |

### 2.2 頁面內容（三塊）

**(1) 先決條件與有效政策** —— 這一塊是本頁最有價值的部分，因為它回答「為什麼我不能建立」：

| 顯示 | 來源 |
|---|---|
| 四個先決條件的勾／叉：ssh 用戶端、對外連線、主機金鑰、**本機未否決** | `02-…md` §2.4 的 node 回報，附 `tunnel_reported_at`（值會過時，要標時間） |
| **有效政策**：可用 port 範圍、隧道上限，並標明**每一項是被哪一層限制的** | `04-…md` §1.1 第 3 步的合成結果 |
| 本機否決時 | 明確寫「此 Node 已在本機停用（`/etc/agentd/config.yaml` 的 `tunnel.enabled: false`），平台無法覆寫」 |

「被哪一層限制」不是裝飾：三層設定（`00-…md` §4）意味著「port 3000 不被允許」有三個可能的原因，而使用者只能改其中一層。不說是哪一層，他就只能一層一層試。

**(2) 該 node 的設定**（寫入 `node_tunnel_settings`，需 `tunnel.manage`）：

- 是否參與（平台側開關）、允許的 port 範圍、隧道數上限。
- 每個欄位旁顯示「全域上限為 X」，且輸入超出全域的值時就地提示「只能比全域更窄」—— **前端不送出必敗的請求**，伺服器仍會擋（D17）。
- 儲存時寫稽核 `integration.node_settings_updated`。

**(3) 隧道清單與建立**：

欄位：port、label、狀態徽章、保護方式、網址、到期（**平台 TTL 與 provider 時限分兩欄** —— 兩個不同的東西，合成一欄會讓「為什麼它自己斷了」無法解釋）、建立者、操作（複製網址／開啟／延長／換密碼／關閉）。

| 決定 | 理由 |
|---|---|
| 「開啟」是 `<a target="_blank" rel="noopener noreferrer">` | D6：新視窗是唯一預設呈現方式。`noopener` 防止被開啟的頁面透過 `window.opener` 操作 console 分頁 |
| 網址旁固定顯示「網址由 Pinggy 指派，可能變更」與 `url_updated_at` 的相對時間 | D9。使用者會把網址貼到別處，平台有義務先講它會過期 |
| `basic` 模式的帳密**只在建立成功的那個對話框裡**顯示，並提供「複製帳密」 | D5。清單中沒有這個按鈕，忘記了就用「換密碼」 |
| 「換密碼」的確認文案必須寫「這會重新建立隧道，**網址可能改變**」 | `04-…md` §2.1：實作是關閉並重開。使用者的心智模型是「改密碼」，不講清楚會有人以為舊網址還能用 |
| `state = failed` 時顯示 `state_error_code` 的文案 | 讀 `utils/errorCatalog.ts`（既有機制），不在前端硬寫 |
| 輪詢 15 秒，且**只在本頁可見時** | `04-…md` §1.2。免費版一小時換一次網址，這個頻率不值得一條推送通道 |
| 建立表單的 port 欄位顯示合成後的允許範圍 | 與 (1) 同一份資料，不要讓兩處算出不同答案 |
| 第一次為此 node 建立時的確認（D14 第二處） | API 回 422 + `requires_acknowledgement` → 顯示四句話的說明並要求勾選。與 `PG-10` §1.2 第 5 塊是**不同的兩個確認**：那是 Admin 決定用這個服務，這是建立者決定這台機器的這個 port 現在對外 |
| `public` 模式的二次確認 | 每次選擇時都要，因為它是逐條隧道的決定 |

### 2.3 驗收

- 單元測試：四個先決條件的顯示、本機否決的文案、有效政策標明限制來源（三種情境各一例）、per-node 設定超出全域時前端就攔、三種保護模式的表單分支、首次確認流程（422 → 勾選 → 成功）、`public` 二次確認、換密碼的確認文案含「網址可能改變」、**「複製帳密」不存在於清單中**（安全相關斷言）、整合未啟用時的顯示。
- Playwright（`frontend/tests/e2e/tunnel.spec.ts`）：以 fake provider 起的 stack（`06-…md` §3.2），Admin 在整合設定頁啟用並存入假憑證 → 到 node 的埠轉發頁建立一條 → 斷言網址出現、`target="_blank"` 與 `rel` 正確、關閉後列表移除。**不真的開啟外部網址**（那會讓測試依賴網路）。

## PG-12：iframe 內嵌與 CSP（選用票，可整票不做）

> **這張票的預設狀態是不做。** 它是本期唯一需要動安全政策的工作，換到的是「少按一次新視窗」。列在這裡是為了讓「要不要做」成為一個有成本資訊的決定，而不是某天有人順手加進去。

### 3.1 要付的代價

| 成本 | 內容 |
|---|---|
| CSP 四處字串 | `deploy/nginx/nginx.conf:134,221,236` 與 `deploy/railway/nginx.conf.template:114,203,216`：`frame-ancestors 'none'` → `'self'`，並新增 `frame-src 'self' https://*.<provider 網域>`。`make railway-check` 的 parity gate 必須同步 |
| **把第三方網域寫進自家安全政策** | provider 換網域（免費版與 Pro 的網域不同，見 `PG-01` #2／#7）就要改 CSP。這是一條長期耦合 |
| 保護模式受限 | Chrome 不在 cross-origin iframe 顯示 basic auth 對話框 → **只有 `ipallow` 與 `public` 能內嵌**。也就是內嵌只在較弱的保護模式下可用，這個組合本身就值得懷疑 |
| 無法偵測拒絕內嵌 | app 若送 `X-Frame-Options: DENY`，跨 origin 的 iframe 沒有可靠的失敗事件。plan/10 用「後端先探測一次」解決，但**本期後端不在資料路徑上，探測不了** |

第四列是與 plan/10 最實質的差別：自建代理時平台可以先 `HEAD` 一次讀 header；整合方案不行，只能提供一個「若畫面空白請改用新視窗」的提示，那是不好的體驗。

### 3.2 若要做，最小形狀

- Session Workspace 的 `tabs` computed（`SessionWorkspaceView.vue:86-110`）新增一個 tab，沿用 `WorkspaceTabs.vue:12-20` 的既有契約，不新增 tab 元件。
- 只有 `protection ∈ {ipallow, public}` 的隧道可選；`basic` 的在下拉中標示「僅能以新視窗開啟」。
- iframe：`referrerpolicy="no-referrer"`、`allow=""`、無 `sandbox`（理由同 plan/10 D19：sandbox 會擋掉多數真實 app，真正的邊界是 origin 隔離）。
- 高度：flex column + `flex: 1 1 auto; min-height: 0`（plan/09 決策 D3）。**不得用 grid 列樣板依子元素順序決定高度** —— CI 有 grep gate。
- 位址列只能顯示「導覽到」的路徑（跨 origin 讀不到真實位置），欄位標籤要誠實。

### 3.3 決策紀錄要求

無論做或不做，都要在 `07-implementation-status.md` 記一筆（決定者、日期、理由）。一個被明確拒絕的選項，比一個沒人提過的選項難被偷偷加回來。
