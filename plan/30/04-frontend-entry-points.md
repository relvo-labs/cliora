# 04 — 前端入口（`FD-06`）

## 1. 顯示條件：兩個，都由伺服器決定

```
canDownloadFiles = capabilities.can_browse_files && nodePosture.file_download
```

- `can_browse_files` 回答「這個使用者可不可以」。
- `file_download` 回答「這台機器可不可以」，且與兩個上傳旗標分開。

**沒有 writer 條件**，理由和一般檔案上傳相同：這條路徑碰的是檔案系統而不是終端機，
所以不需要寫入鎖。兩個人可以同時下載。

旗標為 false 時**隱藏**而不是 disable：一個注定失敗的按鈕比沒有按鈕更糟。

## 2. 兩個入口

### 2.1 預覽工具列

`PreviewPane` 的工具列多一個「下載」。它在**任何有開啟路徑**的時候都可用，
包括編輯器拒絕呈現的那些——「不能在這裡顯示」與「不能交出去」是兩個問題。

下載本身由 view 擁有而不是這個面板，兩個理由：
被拒面板要提供同一個動作，而 composable 的 abort 必須活得比一個中途被關掉的預覽久。

### 2.2 被拒面板（`PreviewDenied`），逐分支決定

這是最有價值的入口：二進位檔正是「顯示」從來就不是問題的那個情況。

| 判決 | 提供下載？ | 為什麼 |
|---|---|---|
| `FILE_BINARY`（二進位） | ✅ | 不能預覽不等於不能取得 |
| `FILE_BINARY`（非 UTF-8） | ✅ | 下載後在本機轉碼，是比 ssh 進去跑 iconv 更短的路 |
| `FILE_TOO_LARGE`，≤4 MiB | ✅ | **兩個上限不同**，中間夾著一段「看不到但拿得走」 |
| `FILE_TOO_LARGE`，>4 MiB | ❌ | 否則按鈕會變成教使用者上限在哪的那個東西 |
| 敏感 | ❌ | 節點用**同一個函式**在下載路徑上也拒絕它 |
| 權限不足／不存在 | ❌ | 會以完全相同的理由再失敗一次 |

最後兩列**還要把話說出來**（「下載同樣被拒」），
而不是留給使用者按一次才發現。這是 UI 唯一有機會暗示相反結論的地方。

## 3. `useFileDownload`

與隔壁的 `useFileUpload` 不對稱，而且不是疏漏：上傳有佇列，
因為使用者一次丟進好幾個檔案而每一個可以用不同方式失敗；
下載由點一個檔案開始，事後沒有東西需要對帳。佇列在這裡會是沒有問題要回答的機制。

它真正擁有的是瀏覽器裡容易做錯的那三件事：

1. **`URL.revokeObjectURL`。** 少了它，每次下載都會讓整個 blob 活到分頁關閉為止；
   在一條 4 MiB 上限的路徑上，一個工作階段累積下來是數十 MB。
   revoke 是延後的，因為 Safari 與較舊的 Firefox 會在 URL 於同一個 task 內消失時取消存檔。
2. **被取代的請求不得把位元組蓋過新的那一個。** 第二次點擊會取代第一次，
   而真實網路仍可能在之後把第一個 body 送到。
3. **取消與被取代要分辨。** `cancel()` 把 controller 設為 null 且不會再有東西來，
   所以這次呼叫仍擁有可見狀態、必須把它重設——否則明確取消會留下一個永遠轉的 spinner。
   被新的 `start()` 取代則不同：新的那次已經為自己的路徑設好狀態，
   在這裡動它會清掉一個仍然為真的 spinner。

（第 3 點是實作時被單元測試抓出來的：第一版在明確取消後狀態卡在 `downloading`。）

## 4. 檔名由伺服器決定

`downloadFile` 回傳 `{blob, filename}`，而 `filename` 來自 `Content-Disposition`——
不是來自路徑，也不是交給 `download` 屬性去猜（`03-…md` §4）。

`filenameFromDisposition` 優先取 RFC 5987 形式。
這個偏好**沒有可見的失敗**：取錯了不會報錯，只會把 `年度統計.csv` 默默存成
`download.csv`，而沒有人會把那件事回報成 bug——他們會改個名字然後繼續工作。
所以它有自己的單元測試。
