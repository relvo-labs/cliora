## 3. 研究者建議與信心（v0.1 原文；已由 §0 的產品決策覆蓋）

**建議：以 A（克制編輯式）為基底，帶進 C 的一條規則——「需要使用者做事時，那個動作是整寬按鈕」**；
B 的「有標籤的狀態格」不採用為預設，但保留為 200% zoom／大字級下的替代排版候選。

理由（依重要性）：

1. 痛點地圖裡最大的問題是結構（P1、P2、P5、P6），三個變體都已解決；在結構相同時，A 的外框最少、終端最多、離 VDS 最近、實作成本最低。
2. A 的弱點是「無標籤的控制權」與「尾端小按鈕容易漏看」；C 的整寬動作按鈕正好補這一點，而且只在 Viewer／斷線時出現，平常不佔高度。
3. B 的標籤最清楚，但每個狀態都多付 30–60px，而且把中文擠進等寬 meta，閱讀最差；它回答的是「資訊密度」，而使用者的回饋是「太制式」，不是「資訊不夠」。

**信心：中低（約 55%）。** 原因寫清楚：

- 沒有任何真機、真人觀察；評等全是研究者判斷。
- A 與 C 在終端畫面幾乎一樣，這個建議其實主要建立在清單與狀態列上。
- 「AI 制式化」是使用者的一句話；我們把它解讀為「外框堆疊＋膠囊＋桌面式提示」，這個解讀本身需要驗證。
- D1／D2（深色終端）可能就是使用者最強烈的感受；它修好之後，對三個變體的偏好可能會變。

## 4. UAT 必須確認的事（v0.2：驗證 C）

在 #103（D1／D2）修正**之後**做（否則測到的是「深色終端 vs 明亮終端」），iPhone Safari 與 Android Chrome 各至少一台，
使用合成資料。每位觀察者以 **C** 完成 U1–U9；只有當 C 在某題失敗時，才用 A 做同一題的對照，判斷問題在 C 的視覺選擇還是在共同 IA。

### 4.1 C 特有、必須回答的四題

| # | C 的選擇 | 風險 | 怎麼測、什麼算通過 |
|---|---|---|---|
| C1 | 清單**不顯示工作目錄路徑**（只有名稱、Runtime、Node、時間） | 名稱相近或同名的 Session，使用者分不出是哪個工作區 | 準備兩個同名、不同路徑的合成 Session（例如 `demo-api` 在兩個工作區）；U1 延伸：「打開 `/srv/demo/b` 那個」。通過：不打開錯的一個就能選對（可接受先打開 `⋯` 確認）。失敗時的調整方向是「只在同名時顯示路徑」，不是回到 A |
| C2 | 內文 16px、行高 1.55 | 一屏內容最少；清單在 390×844 只看得到 4–5 列，活動串更短 | 計時：在 5 個 Session 的清單找到失敗的那一個；活動串找到「進行中」的工具事件。與 A 同題對照差距 >30% 視為失敗 |
| C3 | 12／16px 圓角、白卡浮在灰底、整寬藍色主按鈕 | 被讀成「消費型 App」或通用樣板——正是 #75 要去除的「制式感」的另一種形式 | U8 的開放問題一律不引導；另問「這看起來像哪一類產品？」。若多數答案落在「銀行／外送／一般 App」而非「工程工具」，優先把控制項圓角退回 8px（Q8 選項 b） |
| C4 | 控制權**沒有標籤**（「唯讀 · 他人持有」是一句話，不寫「控制權」三個字） | 使用者看得到字，卻不知道它回答的是「能不能打字」 | U2 原題；另在「你有控制權」狀態問「你現在打字，會送到哪裡？」。通過：不看終端就能回答。失敗時的調整方向是只加回這一格的標籤（B 的做法），不改整條狀態列 |

| # | 任務／問題 | 通過條件 |
|---|---|---|
| U1 | 打開清單，指出哪個 Session 失敗、哪個在另一台 Node | 不需要點開 |
| U2 | 在 Viewer 狀態下，回答「你現在能打字嗎？為什麼？怎麼做？」 | 不解讀終端內容即可回答（#75 驗收第 2 項） |
| U3 | 斷線狀態：「畫面上的輸出是最新的嗎？」 | 能說出「不是／已停止更新」 |
| U4 | 可提權 Node：「這台機器有什麼要注意的？」 | 能說出 sudo／root 或沙箱停用 |
| U5 | 從活動（假說）或預覽拒絕回到原生終端 | 一次點擊內完成 |
| U6 | 開啟系統 shell，再說出它與「終端機」分頁的差別 | 能說出「關掉會終止」或「不受工作目錄限制」 |
| U7 | 轉成橫向繼續看輸出 | 不迷路、終端仍可讀 |
| U8 | 開放問題：「哪一版比較不像『AI 樣板』？為什麼？」 | 記錄原話，不引導 |
