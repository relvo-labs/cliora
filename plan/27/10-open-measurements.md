# 10 — 本期知道自己沒量的東西

> 格式沿用 [`plan/26/11`](../26/11-open-measurements.md)：
> **是什麼／為什麼現在不量／何時量／風險由誰承擔**。
> 前四項是從 `beta.1` 與上游繼承過來、**本期要收掉**的；
> 後六項是本期新產生的。

## 繼承並在本期收掉的四項

### 1. 十級 authority 是否過細（上游 §10 #7）

**是什麼**：`alpha.3` 的 D45 定了十級。上游把「是否過細」排在 `beta.1`，
`plan/26/11` §7 把它移到本期。

**本期怎麼量**（[D134](./01-decisions-and-governance.md#d134)）：
`context_citation_total{authority}` 十個 counter，**只記 metadata**。
一個 release window 之後，看有沒有任何一級是 0 次。

**為什麼本期終於量得到**：`reviewed` 這一級在 `alpha.3` 就有權重（1.15）
但**沒有寫入者**（`store.py:36` 的 docstring 自己這樣寫）。
本期的 `HD-02` 是它第一個寫入者，所以這是十級第一次全部有來源。

**判準**：任何一級 0 次 → 合併它的討論有了對照組。
`store.py:37` 已經寫過方向：「merging levels later is a migration while splitting one
later is a judgement about rows written before the distinction existed」——
**合併是可以做的那一個**。

**風險由誰承擔**：若沒有人看這個數字，D45 的十級就從一個設計退化成一個現況。

### 2. `cliora task wait` 的 120 秒上限（上游 §10 #8）

**是什麼**：`alpha.2` 的 `CV-08` 訂了 120 秒。

**本期怎麼量**（[D135](./01-decisions-and-governance.md#d135)）：
十八條旅程跑的時候記下每一次 `task wait` 實際等了多久、有沒有撞到上限。

**為什麼不改**：`daemon` diff 為零（[D131](./01-decisions-and-governance.md#d131)）。
一個沒有資料支撐的常數調整只是換一個沒有資料支撐的常數。

**風險由誰承擔**：若十八條裡有任何一次撞到上限，
那是一個要進 `rc` 的 blocker 而不是一個要記在這裡的觀察。

### 3. 300 行自製 query 層的維護成本（上游 §10 #3）

**是什麼**：`plan/26` D100 造了 `modules/work/queryCache.ts`，不用套件。

**本期怎麼量**（[D136](./01-decisions-and-governance.md#d136)）：
數 `git log --oneline -- frontend/src/modules/work/queryCache.ts` 的筆數，
**逐筆寫「為什麼改」**。

**判準**：若有任何一筆是「為了讓某個畫面能用而在快取層開一個特例」，
那是「自製」的成本開始顯現的訊號，要進 `v2.1.0` 的 discovery。
**若一次都沒改，那也是一個答案**——而且是好的那一個。

**為什麼不做問卷**：一個問「這個檔案好不好維護」的問卷，
答案取決於回答的人有沒有改過它。commit 數不取決於這個。

### 4. 大 Project（>2000 卡）的分頁與 counts（`plan/26/11` §10）

**是什麼**：`beta.1` 全部量測用 200 卡。

**本期怎麼量**：`HD-10` 的 2000 卡固定資料集（[`06`](./06-scale-and-observability.md) §2）。

**本期之後仍然沒量的**：**2000 卡以上**。
這一項因此不是被收掉，是**被推進了一格並重新寫下界限**——
而那個界限要進 known limitations（[`09`](./09-verification-and-exit.md) §7 第 3 條）。

**風險由誰承擔**：運維。而 known limitations 那一行就是把風險交出去的方式。

## 本期新產生的六項

### 5. `pull_request` 與 `release` 的半衰期（90／365 天）

**是什麼**：[D121](./01-decisions-and-governance.md#d121) 給了兩個數字，
理由是「PR 討論像 artifact、release 像 decision」。

**為什麼現在不量**：需要一個跑了幾個月、有真實檢索紀錄的 index。

**何時量**：與 `KN-12` 的 relevance eval 同一批（那組基準就是對照組）。

**風險由誰承擔**：若 release 的半衰期太短，
「v1.4 有什麼」這個問題會在一年後找不到答案；
若 PR 的太長，兩年前一個被否決的提案會排在昨天的規格前面。
**`.get(…, 90.0)` 的預設讓漏掉不會崩**，所以這兩個數字要被明寫是**刻意選的**
而不是撿到預設值——`test_every_source_type_has_an_explicit_half_life` 是這一句的執行。

### 6. `maxDiffPixelRatio: 0.01` 這個門檻

**是什麼**：[D124](./01-decisions-and-governance.md#d124) 的視覺回歸門檻。
1440×900 上約 13000 個像素。

**為什麼現在不量**：需要跑過幾十次才知道誤報率。

**何時量**：本期結束時數一次誤報次數。**若 > 0 就調高並記錄理由。**

**風險由誰承擔**：開發。而風險的形狀很具體——
`plan/26` §6 那一段（「一個附了理由的空方框會被接受」）的視覺版本是：
**一套誤報三次之後被加上 `--update-snapshots` 的回歸套組，
在儀表板上與一套有效的套組長得一樣。**

### 7. 300 秒這個 reconcile 間隔

**是什麼**：[D128](./01-decisions-and-governance.md#d128) 沿用
`worker.py:49` 的 `RECONCILE_INTERVAL_SECONDS = 300.0`。

**為什麼現在不量**：「一個 PR 合掉之後多久要看到」是一個關於**團隊節奏**的問題，
不是關於系統的。一個每天發五次的團隊與一個兩週發一次的團隊，
答案差一個數量級——而本期沒有任何真實團隊在用。

**何時量**：`beta.2` 上線後。量的是**有多少人在等**——
若有人在 Drawer 上按重新載入超過一次，300 秒就太長了。

**風險由誰承擔**：產品。而它有一個對照：
`alpha.2` 的「message commit → continuation turn P95 < 10s」是同一類的承諾，
而那個數字當時也是猜的（`research/03/01` §1.2 記著它從 2s 放寬到 10s 的理由）。

### 8. 「連續 3 次失敗停止同步」這個 3

**是什麼**：[D128](./01-decisions-and-governance.md#d128) 的退避門檻。

**為什麼現在不量**：3 次 × 300 秒 = 15 分鐘。
這個數字要平衡「一次暫時性的網路問題不該讓同步停掉」
與「一個被撤權的 token 不該燒一小時的配額」。

**何時量**：`beta.2` 上線後看 `provider_read_total{outcome="unreachable"}` 的分布。
若絕大多數是單次失敗然後自己好了，3 太小。

**風險由誰承擔**：運維。而**它有一個緩解**：
設定頁上顯示 `provider_sync_error`（[`02`](./02-provider-ingestion.md) §6），
所以停掉這件事至少**看得到**——這與「什麼都不再更新」的沉默失敗不同。

### 9. `work-counts` 在 2000 卡上會不會超過 200ms

**是什麼**：`plan/26` D95 訂的硬預算，在 200 卡上量的。

**為什麼算未量測而不是未達成**：本期會量它（`HD-09`），
但**寫這份計畫時不知道答案**，而處置取決於答案。

**三個處置，按優先序**：①加索引 ②輪詢從 20 秒調長 ③列入 known limitations。
**不許做的是把預算調高而不說。**

**風險由誰承擔**：使用者。`work-counts` 是最熱的端點
（每個開著的看板分頁每分鐘問三次），所以它慢的表現是整個 app 都慢。

### 10. `HD-06` 能不能在本期做

**是什麼**：[D123](./01-decisions-and-governance.md#d123) 的 go／no-go 四項，
其中第一項是「`beta.1` 已部署在一個有真實資料的環境」。

**為什麼算未量測**：寫這份計畫時 `v2.0.0-beta.1` **沒有 tag、沒有部署**，
所以 ambiguous report **不存在**。

**何時知道**：`HD-06` 的第一個動作——**確認能不能拿到它**，
而不是開始寫 migration。

**風險由誰承擔**：這一項的風險是**它會被悄悄跳過**。
所以 [D139](./01-decisions-and-governance.md#d139) 把「跳過也要寫下來」
變成出口條件第 3 項，而 [`09`](./09-verification-and-exit.md) §7 的第 8 條
是那個後果的預先記錄。

## 一句話

**這十項裡有六項的處置是「量一個數字然後看它」**，
而它們共同的失敗模式不是量錯，是**量了之後沒有人看**。

`plan/26/11` §9 已經寫過這一句的一個版本
（「如果比率很高而沒有人看這個數字，D97 的『維持警告』就從一個決定退化成一個現況」）。
本期把它做成一個機制：**§1、§3、§6、§7、§8、§9 六項的數字，
在 `HD-12` 的 release note 裡各佔一行**。
一個必須被寫進 release note 的數字，至少會被讀一次。
