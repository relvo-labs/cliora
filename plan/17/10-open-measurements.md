## 1. M1 — 200 張卡的看板 API（**開工前必須有答案**）

`research/02/10` §5 列為 V2.1 開工前的量測。`TK-00` 交付（`01-…md` §2.2）。

| 項目 | 內容 |
|---|---|
| 問題 | 一個 200 張卡的專案，`GET /api/projects/{id}/board` 的回應大小與耗時？ |
| 影響 | **看板端點要不要分頁**——而形狀改了前端就要改 |
| 做法 | `scripts/tk/seed_board_fixture.py` 造 200 張卡（每張 5 條 AC、7 項 readiness、6 個 gates、平均 1.5 條相依），量 gzip 前後位元組、p50／p95 伺服器耗時、前端首次可拖曳時間 |
| 判準 | 回應 > 512 KB 或 p95 > 400 ms → 逐車道分頁（每車道 50 ＋ `has_more`），摘要不含 AC 全文與 gates 明細 |
| 結果 | ☑ **已量（2026-08-09）**，見下 |

```text
scripts/tk/measure_board_payload.py --cards 200        → artifacts/tk/local/m1.json
  full 形狀（含 AC 全文 ＋ 六個 gates 明細）   439,029 bytes   gzip 31,983
  summary 形狀（看板實際渲染的欄位）            73,851 bytes   gzip 12,665
  門檻                                        524,288 bytes
--cards 500（壓力點）
  full                                      1,095,789 bytes   ← 已破門檻一倍
  summary                                     184,205 bytes

frontend/tests/e2e/tasks.spec.ts --grep M1             → artifacts/tk/local/m1-live.json
  真實 PostgreSQL + Central HTTP，200 張卡，50 次取樣
  實際 response                               61,748 bytes
  p50                                             7.98 ms
  p95                                             9.37 ms
  門檻                                          400.00 ms
```

**裁決：看板端點回 summary 形狀，不分頁。**

三個從數字讀出來的結論：

1. **決定成敗的是形狀，不是分頁。** summary 在 200 張卡只有 72 KB、在 500 張卡也只有 180 KB，
   離門檻還很遠；full 在 200 張就已經是 439 KB，**500 張直接破一倍**。
   換句話說：分頁能買到的東西，把 AC 全文與 gates 明細移出摘要就已經買到了，而且不必付
   游標、`has_more`、前端捲動載入與 e2e 的代價。
2. **所以 `plan/17/03-…md` §3.1 的「摘要一律不含 AC 全文與 gates 明細」從建議升為硬規則**，
   並配一條測試：board 回應的任一張卡都不得含 `acceptance_criteria` 或 `gates` 的明細
   （只回 `gates_approved_count`）。這條測試守的不是效能，是**這次量測的結論不被日後一次
   「順手多回一點」推翻**。
3. **`has_more` 仍然要在 DTO 裡**，值恆為 `false`。一個之後才加的欄位會讓每個既有客戶端
   都要處理「沒有這個欄位」的情況；一個從第一天就在的欄位，日後真的需要分頁時是一次
   伺服器端的改動。

**耗時量測已在 `TK-04` 落地後補齊。** 數字來自 live-stack 的真實 PostgreSQL、Central
HTTP 路徑與完整 response body read；5 次暖機後取 50 次樣本。它是同機 loopback 的回歸
基線，不代表廣域網路延遲，但回答的是「伺服器查詢／序列化是否已逼近 400 ms 門檻」。
目前 p95 只有門檻的 7%，維持 summary 單次回應、不分頁的裁決。

## 4. 沒有要量什麼，以及為什麼

沿用 `plan/16/08` 的既有段落形狀——寫下「刻意不量」比留白好，
否則下一期會有人以為是漏掉的。

| 沒量 | 為什麼 |
|---|---|
| **sidebar 寬度（M8）** | 本期**沒有新的導覽項**，全部在 Project 詳情頁的分頁下（`07-…md` §1）。V2.2 加 `Agents` 時才要重量，那時 `plan/09` 的高度規則也要複驗 |
| 拖曳的互動延遲 | 樂觀更新讓感知延遲等於零；真正會慢的是失敗後的重新載入，而那是一次單卡 GET |
| `session_tokens` 的表成長 | 一個 Session 一列，而 Session 本來就有既有的量級。90 天保留期是照抄既有的 audit 保留期慣例，不是算出來的——**若 M7 顯示 Session 量級遠大於預期再回來看** |
| 情境包產生的伺服器耗時 | 它是一次 DB 讀 ＋ 字串組裝。若 M-TK-01 顯示往返慢，慢的會是網路與 daemon 寫檔，不是這裡 |
| Agent 在 `.cliora/process/` 實際讀了幾份 | 讀檔發生在 node 上，平台看不到。這是 D2 選項 A 的已知代價（投影出來的說明不會被自動載入），**M2／M3 是它的間接指標** |
