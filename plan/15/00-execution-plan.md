# 00 — 執行總控（一般檔案上傳：拖進檔案瀏覽器）

Ticket 前綴 `FU-`（**F**ile **U**pload）。取代已作廢的 `plan/14`（`01-…md` §6）。

## 1. 成功定義

**要交付的：** 使用者把一個檔案從桌面拖進瀏覽器的檔案樹，放在他選的那個目錄上，
檔案就以原本的名字出現在節點的工作區裡，CLI 讀得到它。

**其餘一律不做。** 編輯、更名、刪除、下載、資料夾上傳 —— 使用者明確指示
「其餘就用 cli 或是 terminal 處理」，所以本期的每一個「不做」都不是妥協，
而是被指定的範圍（§2）。

**不得弄壞的五件事：**

1. **`os.Root` 的封閉性。** 新的落地路徑與既有的讀取面、圖片投放面共用同一個
   `workspace.Root`（ADR 0014、`SEC-001`、ADR 0024 W1）。`daemon/` 底下不得出現
   任何吃工作區絕對路徑的 `os.WriteFile`／`os.Create`。
2. **永遠不覆寫。** 落地一律 `O_EXCL`；同名檔案存在就拒絕，由使用者改名或取消。
   這一條是本期能夠**不需要**版本前提、不需要回收桶、不需要 undo 的唯一原因（D2）。
3. **平台不寫入它自己不肯顯示的位置或名字。** 目的地與檔名都要過讀取面
   **同一個** `SensitiveClassification()`；`.git/`、`.cliora/`、排除目錄、
   工作區根目錄以外的規則一律共用（D4）。
4. **落地的檔案不可執行。** 一律 `0644`，不看來源、不看副檔名（D6）。
5. **圖片投放（ADR 0024）不受影響。** `.cliora/uploads/` 那條路徑、
   它的貼上入口、它的配額與清理，本期一個位元組都不動（D10）。

成功的判準是這九項，每一項都要有可貼上的輸出（`05-…md` §3）：

1. 把一個 `data.csv` 拖到檔案樹的 `datasets/` 那一列上，該列出現一個新的
   `datasets/data.csv`，節點上該檔存在、SHA256 與來源相同、權限是 `0644`。
2. 同一個檔案再拖一次，得到 `FILE_EXISTS`，**節點上的檔案沒有被改動**
   （mtime 與 SHA256 都不變），UI 提供「改名」與「取消」。
3. 一次拖三個檔案進來，三個都落地，上傳列各有一列狀態；其中一個超過大小上限時
   **只有那一個失敗**，另外兩個仍然成功。
4. 拖一個**資料夾**進來，得到一句「資料夾請用終端機處理」，**沒有發出任何請求**。
5. 用工具列的〔上傳檔案〕按鈕選同一個檔案，結果與拖放**完全一致**（同一條程式路徑）。
6. 拖到 `.git/` 那一列、`.cliora/` 那一列、`node_modules/` 那一列上，
   分別被拒且分類正確；把檔案取名為 `.env` 上傳，被拒；
   **以上每一種情況節點上都沒有產生任何檔案**。
7. Viewer 看不到上傳入口，且直接呼叫 HTTP 端點得到 403，`authz.denied` 有一筆。
8. 每一次成功上傳留下一筆 `file.upload` 稽核，metadata 有使用者、session、節點、
   **使用者選的相對路徑**與位元組數，沒有內容。
9. 關閉 `filesystem.upload.files.enabled` 的節點回報 `file_upload: false`，
   UI **不顯示**上傳入口，而且拖放不會有任何反應（不是顯示一個按了會失敗的提示）。

## 2. 範圍

### 納入

- `FU-01` 四項行為實測（`07-…md`），其中第 1 項是**閘門**。
- `FU-02` ADR 0026、ADR 0024 的 W2 加註、PRD 修訂（新增 `FR-FILE-010`、
  `NFR-005.AC-109` 再收窄、`NFR-005.AC-142` 一句話修訂）、traceability 註冊。
- daemon：`files/store.go`（一個動詞的 default-deny 順序）、寫入方向的名稱與位置政策、
  可用空間檢查、配額、設定、`doctor`（`FU-03`）。
- 契約 v1.9.0（compatible）：一對型別 `filesystem.store`／`filesystem.stored`、
  `node-register.file_upload` 一個回報欄位、六個 golden fixture（`FU-04`）。
- Central：`POST /api/sessions/{id}/files/upload`、沿用 RBAC `file.upload`、
  沿用稽核 `file.upload`、五個錯誤碼、`can_upload_files` 沿用、migration `0020`（`FU-05`）。
- 前端：檔案樹的放置目標與高亮、上傳佇列與逐檔狀態、〔上傳檔案〕按鈕、
  同名衝突的改名流程（`FU-06`）。
- `.agent/skills` 修訂兩份、evidence／gates／runbook／release note（`FU-07`）、
  安全審查與 exit gate（`FU-08`）。

### 不納入

以下每一項都是**使用者指定的範圍外**，不是能力不足：

- **編輯檔案內容。** 用 CLI 或終端機。
- **更名、刪除、建立目錄。** 用 CLI 或終端機。
- **下載。** `NFR-005.AC-109` 剩下的最後一片，仍是未來擴充。
- **上傳資料夾**（含 `webkitGetAsEntry` 的目錄遞迴）。拖進來會被明確拒絕（D9）。
- **覆寫既有檔案。** 見 D2。這是本期最重要的一個「不做」。
- **分塊上傳。** 因此有一個單檔上限（D3），超過的檔案用終端機。
  觸發條件與後續路徑寫在 D3 的「日後」欄。
- **版本前提、回收桶、undo、衝突合併、dirty 狀態機。** 這些是 `plan/14` 的機制，
  而它們全部只為了「覆寫」與「刪除」存在。本期不覆寫也不刪除，所以一個都不需要。
  這就是 `plan/14` 與本計畫在規模上的全部差別（`01-…md` §6）。
- **改動圖片投放。** 見 D10。

## 3. 固定基線決策

| # | 決策 | 選擇 | 理由 |
|---|---|---|---|
| D0 | **本期在 ADR 0024 的哪一格** | ADR 0024 的 rejected 表列著「Open general file upload, since writes are allowed now」，理由是「W2／W3／W4 must hold for general upload too, and they are not designed for it — starting with what a quota means for arbitrary file sizes」。本期**就是**去設計那三條，而不是主張它們不適用 | 那一列不是「永遠不做」，是「還沒設計」。把它當成禁令會做不出使用者要的東西；把它當成不存在會漏掉它點名的三個問題。W2 的答案在 D5（而且它需要修訂 W2 的措辭，見 `01-…md` §2），W3 在 D8，W4 在 D7 |
| D1 | **請求端可以命名檔案與目錄，而這正是 ADR 0024 §4 預告的情況** | wire 上有 `directory` 與 `filename` 兩個欄位。**但不是加在 `filesystem.upload` 上** —— 那是圖片投放的型別，它的整個設計就是「請求端不得命名」。本期新增**另一個**型別 `filesystem.store`，帶自己的一套防護（D4） | ADR 0024 §4 寫得很明確：那條「不得命名」的規矩**不是通則**，而且它同時擋掉兩個相反的錯誤 —— 一是拿它當先例主張任何路徑都不能被指名（那會做不出這個功能），二是拿本期當先例回頭在 `filesystem.upload` 上加一個 `filename`（那會白白弄壞一條已經正確的路徑）。**兩個型別並存，各自的規矩各自成立**，這是本期唯一正確的形狀。差別在於：截圖不需要名字，`requirements.txt` 的名字就是它的全部意義 |
| D2 | **永遠不覆寫** | 落地一律 `O_EXCL`。同名檔案（或目錄、或 symlink）已存在 → `FILE_EXISTS`，不落地、不改動既有檔案。UI 提供「改名後重試」與「取消」 | **這一條買下了整個 `plan/14` 的機制。** 覆寫要安全就需要版本前提、412、回收桶、undo 與衝突 UI；不覆寫就一個都不需要，因為**沒有任何既有位元組會被動到**。而使用者要的是「把檔案放進工作區」，不是「取代工作區裡的檔案」—— 後者他有終端機。**被否決**：自動加尾碼（`data (1).csv`）—— 靜默改名會讓 CLI 讀到舊的那一份，而使用者以為它讀到新的，症狀是「AI 看的是舊資料」；覆寫加一個 `overwrite: true` 旗標（那就是 `plan/14` 的第一步，然後每一個機制都會跟著回來） |
| D3 | **單檔上限** | 沿用圖片投放的 `filesystem.upload.max_bytes`（預設 **4 MiB**），**一個設定鍵管兩條路徑**。超過回 `FILE_UPLOAD_TOO_LARGE`，文案直接說「較大的檔案請在節點上以終端機處理」 | 上限的來源是**訊框**而不是偏好：4 MiB 原始位元組 → base64 5.33 MiB → 在既有的 8 MiB `MaxFilePayload` 之內，所以**契約的訊框上限一個位元組都不用動**（ADR 0024 §7 已經為圖片付過那次代價）。新增一個 `TestUploadCapFitsFrameBound` 斷言，讓「把上限調大」這件事會撞到一個會說話的測試而不是一個沉默的截斷。**日後**：若上線後 `FILE_UPLOAD_TOO_LARGE` 佔上傳嘗試 >10%（由 `05-…md` §3 的 metric 觀測），再決定分塊上傳 —— 那是一個新 ADR（狀態機、逾時清理、部分落地的收尾），不是一個參數。**被否決**：現在就做分塊（使用者剛剛才說改動過大）；把訊框上限提高到 12 MiB（要動所有 large-frame 型別的解碼上限，而 uvicorn 的 `ws_max_size` 是 16 MiB，餘裕變薄） |
| D4 | **可寫的位置與名字＝可讀的位置與名字** | 目的地目錄與檔名合成的相對路徑，必須通過讀取面**同一個** `policy.SensitiveClassification()`，並額外擋掉四類：`.git`（**含 worktree 那種作為檔案存在的形式**）、`.cliora/`、`workspace.excluded_directories` 的任一片段、工作區根目錄以外不存在的目錄 | 一句話：**平台不寫入它自己不肯顯示的位置或名字。** 四個好處：(a) 回答 ADR 0024 §4 留給「客戶端指名」的防護問題；(b) 不會出現「上傳成功但平台自己拒絕顯示」的黑洞（例如 `.env`）；(c) 敏感檔案政策只有一份實作；(d) 一個秘密不會因為使用者拖錯檔案而經過 Central 的中繼路徑。**被否決**：寫入方向放寬（「那是他自己的檔案」）—— 使用者真的要把金鑰放上節點時有終端機，而那正是他自己指定的分工 |
| D5 | **W2 的第三腿：保留期不適用，取代它的是可見性** | 單檔 4 MiB（D3）＋每 session 累計 **256 MiB**＋每日 **200 個檔案**＋**可用空間下限**（低於 512 MiB 或不足檔案大小的兩倍就拒絕）。**沒有保留期，也不該有** | ADR 0024 的 W2 寫「per-operation size, cumulative quota, and a retention period — all three」。保留期存在的理由是**平台自有的目錄不能無界成長**（`.cliora/uploads/` 由平台命名與擁有，所以 7 天清掉）。但本期的落地位置是**使用者選的**，那個檔案從落地的那一刻就是他的資料 —— 平台七天後把它刪掉會是災難，而不是紀律。所以 W2 對這條路徑的正確形狀是：**平台不累積任何看不見的東西**。每一個上傳的檔案都在使用者選定的路徑、出現在檔案樹上、由他自己清理，與他的 CLI 寫出來的檔案沒有兩樣。**這是 ADR 0024 的 W2 需要一句修訂**（`01-…md` §2），不是一個 waiver。可用空間下限是為了補上保留期原本擋的那個風險（磁碟填滿），而且它擋得更直接 |
| D6 | **落地的權限固定 `0644`** | 不論來源檔案在使用者機器上是什麼權限，落地一律 `0644`；目錄不建立，所以沒有目錄權限的問題 | 一個從瀏覽器拖進來的檔案不應該是可執行的。使用者要它可執行時的動作是 `chmod +x`，那是一個他知道自己在做什麼的動作 —— 而「拖進來就能跑」是一條不需要存在的路徑。這一條也讓「上傳的東西會不會被當成別的東西執行」在安全審查上有一句話可以回答 |
| D7 | **節點可以拒絕**（W4） | 新設定 `filesystem.upload.files.enabled`（預設 **`true`**），以 `node-register.file_upload` **回報**；UI 依回報決定是否顯示入口。**與圖片投放的 `image_upload` 是兩個獨立的開關** | 兩個開關不合併，因為它們問的不是同一個問題：「平台可以把截圖放進 `.cliora/`」與「平台可以把任意檔案放到我工作區的任意位置」對節點擁有者是不同大小的授權。沿用 1.7.0 的 report-only 形狀。預設 `true` 的理由與 ADR 0023 D2、ADR 0024 D8 相同（**升級即取得新行為**），因此同樣要有 release note 與 runbook，不得靜默 |
| D8 | **RBAC 與稽核都沿用 `file.upload`**（W3） | 不新增 action，不新增稽核事件。`file.upload` 的**語意擴大**：從「把一張圖片投放到平台自有目錄」變成「把一個檔案放到工作區裡的一個位置」。稽核 metadata 的 `path` 從「平台取的名字」變成「使用者選的路徑」，其餘欄位不變 | 這是本期唯一一個「擴大既有東西」而不是「新增東西」的決定，所以理由要寫足：(a) 動詞是同一個（上傳），拆成兩個 action 會讓稽核查詢要 union 兩個鍵；(b) 三個固定角色底下沒有人能組出「可傳圖不可傳檔」；(c) `ROLE_ACTIONS` 有三重自動檢查，每多一個 action 就多三處要維護；(d) 持有者（Admin＋Developer）本來就同時持有 `terminal.operate`，在同一台節點上可以直接寫檔 —— 本期是新介面不是新能力。**代價要寫在 ADR 與 release note**：一個曾經只授權截圖投放的組織，升級後那個授權變大了。**被否決**：新增 `file.write`（`plan/14` 的做法，會帶來一個 seed migration 與三處矩陣維護，換到的只有一個沒有人會分開設定的旗標） |
| D9 | **資料夾不上傳** | `DataTransfer` 裡任何一個項目是目錄（`webkitGetAsEntry().isDirectory`）→ 整批拒絕，顯示一句「資料夾請用終端機處理（`git clone`／`scp`／`tar`）」，**不發任何請求** | 資料夾遞迴要處理：建目錄（本期不建目錄）、數量無界、部分失敗的收尾、以及一個進度模型。使用者已經指定「其餘用 cli 或 terminal 處理」，而資料夾正是那一類。**整批拒絕而不是跳過目錄只傳檔案**：靜默跳過會讓使用者以為整個資料夾都上去了 |
| D10 | **圖片投放一個位元組都不動** | `.cliora/uploads/`、貼上入口、`SniffImage`、它的配額與 7 天清理、`filesystem.upload` 這個型別與它的 fixture，全部不變 | 它兩天前才上線並實測過。本期是**加一條路徑**，不是重構既有的那條。判準：若 diff 出現在 `daemon/internal/files/upload.go` 的判斷邏輯、`useImageDrop.ts`，或任何 `filesystem.upload` 的 fixture，就是走錯路了。**唯一允許的共用是往下的**：`store.go` 可以呼叫 `upload.go` 已經寫對的小工具（`ensureClioraDir` 不需要、`writeAndSync` 需要），但不能反過來改它 |
| D11 | **多檔一次拖放，循序上傳** | 一次最多 **20 個**檔案，**循序**（不併發）送出，每一個檔案在上傳列有自己的一列狀態，一個失敗不影響其他 | 循序而不是併發：一個節點的連線是共用的，而 4 MiB × 20 併發會把控制訊框的通道塞住（`filesystem.store` 是大訊框型別）。20 個的上限是為了讓「不小心拖了整個下載資料夾」有一個明確的拒絕而不是 200 個請求。**被否決**：一次一個檔案（使用者拖三個 CSV 進來是常態）；併發（見上） |
| D12 | **這一期不碰的東西** | terminal relay 與 single-writer、ws-ticket、backpressure、tunnel、daemon update、edge nginx、CSP、檔名搜尋、文字判定、預覽政策、圖片投放 | 判準：若 diff 出現在 `backend/app/api/ws/`、`deploy/`、`daemon/internal/tunnel/`、`daemon/internal/update/`、`files/policy.go` 的 `Classify()` 函式本體，就是走錯路了。**已核對**：`client_max_body_size` 兩處都已是 `16m`，4 MiB 的請求體不需要任何 edge 變更 |

## 5. 風險

| 風險 | 徵狀 | 處置 |
|---|---|---|
| **使用者以為上傳會覆寫，結果拿到一個錯誤** | 「為什麼我更新不了那個檔案」 | D2 是刻意的，所以 UI 要把它講成規則而不是失敗：同名時直接給一個預填好新名字的輸入框，並在旁邊寫「要取代既有檔案請在終端機處理」 |
| **4 MiB 不夠用** | 使用者常常拖進被拒絕的檔案 | D3 的 metric 是觸發條件而不是猜測。文案必須立刻告訴他替代路徑（終端機），不能只說「太大」 |
| **`file.upload` 的語意被靜默擴大** | 一個組織發現 Developer 現在可以往工作區任意位置寫檔 | D8 的代價要寫進 ADR 與 release note 的第一段，而不是附註。這是本期唯一一個對既有授權的改動 |
| **秘密經由拖放進到節點** | 使用者把 `.env` 或 `id_rsa` 拖進來 | D4 擋名字（讀取面同一份規則）。要注意這**不是**完整的防護 —— 使用者可以把 `.env` 改名為 `notes.txt` 再拖進來，而那是他自己的檔案、他自己的節點。政策擋的是**誤操作**與**平台的共犯性**，不是使用者的意圖。這一句要寫進安全審查 |
| **拖放弄壞了終端機的圖片投放** | 拖圖到終端機沒反應，或拖檔到樹上被當成圖片 | 兩個放置目標是不同的 DOM 子樹，但要有一條測試同時斷言兩者；另外要在 view 層攔掉落在兩者之外的 drop，否則瀏覽器會直接開啟那個檔案（`04-…md` §1.4） |
| **磁碟被填滿** | session 起不來 | D5 的三個上限＋可用空間下限；`doctor` 增加一行；runbook 寫「怎麼找出誰上傳了什麼」（稽核） |
| **`plan/14` 的機制被「順手」帶回來** | PR 裡出現 `revision`、`precondition`、`trash` | 判準寫死：本期 wire 上不存在 `precondition`、`revision`、`overwrite`，而 `GATE-FU-NO-OVERWRITE` 會 grep 它們（`05-…md` §3） |
