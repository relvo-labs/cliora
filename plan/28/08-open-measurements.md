## 1. 終端列數與字格高度（**閘門**）— 已量測，chromium 通過

**問題：** 五份設計文件寫「終端預設 14px，行高 1.6」。1.6 是 UI 內文的慣例值；
xterm 的 `lineHeight` 是**乘在量測到的字格高度上**的倍率，不是 CSS 的 line-height。
照字面實作會把終端的列數大幅砍掉，而 `plan/09` 的閘門是 **1440×900 下 ≥ 30 列**。

**怎麼量的：** `scripts/vr/xterm-geometry-probe.mjs`。不需要後端也不需要 dev server
——這個問題是 xterm 自己的，不是 Cliora 這一疊的。把 host 設成本期目標幾何留給
CLI 面板的**確切**高度（1440×900 → 674px；1024×768 → 542px），
`fontFamily` 用本期要落地的純本機等寬堆疊（ADR 0016，沒有 webfont），
逐一建 terminal、`fit()`、讀 `terminal.rows` 與
`_renderService.dimensions.css.cell.height`。

### 實測（chromium 1228，2026-09-08）

**1440×900，面板 674px（`plan/09` 的閘門就在這個尺寸）**

| 字級 / 行高 | 字格高度 | 列數 | 欄數 | 判定 |
|---|---:|---:|---:|---|
| 13 / 1.0（目前設定） | 15px | **44** | 118 | 通過 |
| 13 / 1.2 | 18px | 37 | 118 | 通過 |
| 13 / 1.4 | 21px | 32 | 118 | 通過 |
| 13 / 1.6 | 24px | 28 | 118 | **不通過** |
| 14 / 1.0 | 16px | 42 | 110 | 通過 |
| **14 / 1.2（D12 的提案）** | **19px** | **35** | 110 | **通過，餘裕 5 列** |
| 14 / 1.4 | 22px | 30 | 110 | 通過（**正好壓線**） |
| 14 / 1.6（文件字面） | 25px | **26** | 110 | **不通過** |

**1024×768，面板 542px（`plan/09` 沒有在這個尺寸設閘門，記錄供參考）**

|---|---:|---:|---:|
| 13 / 1.0 | 15px | 36 | 83 |

### 結論

1. **D12 成立，而且比推算好。** `14px / 1.2` 在閘門尺寸給 **35 列**，
   餘裕 5 列而不是計畫原本推估的 2 列（原推估把字格高估成 21px，實際是 19px）。
2. **`14px / 1.6` 確實會跌破閘門**（26 列）。五份設計文件的「行高 1.6」
   必須改（`01-…md` M5），這一項不是偏好而是硬性衝突。
3. **`14px / 1.4` 正好是 30 列。** 不要選它——它沒有餘裕，
   任何一個未來的 8px（多一條提示列）都會讓閘門變紅。
4. **1024×768 下 `14/1.2` 只有 28 列。** 那個尺寸沒有閘門，
   但這是一個真實發現，處置寫在 §1.1。

### 1.1 由實測長出來的一項新工作

1024×768 的 542px 面板，扣的是與 1440×900 相同的 224px 固定高度
（header 56 ＋ fill 內距 24 ＋ 工作標頭 72 ＋ 分頁 44 ＋ 狀態列 28）。
在 768px 高的視窗上，那 224px 佔了 **29%**。

處置（進 `VR-04`，不新增票）：**1024–1439px 這一段，工作標頭從兩列 72px 收成
單列 48px**（Session 名稱一列，Node／Runtime／路徑改為可展開）。
面板因此回到 566px，`14/1.2` 給 29 列——仍然不到 30，
所以**同時**倚賴使用者可調字級（12–20px，`FR-TERM-001.AC-16`）：
`13/1.2` 在該尺寸給 30 列。

這一段要寫進 `03-…md` §5 的斷點表，並在 release note 說明
「小視窗建議把終端字級調到 13px」。

## 2. 切換主題不重建終端（**閘門**）— 已量測，通過

**問題：** 本期的核心承諾是「切主題不中斷工作」。它成立的前提是
`terminal.options.theme = {...}` 會就地重繪，而不是清空 buffer。
xterm 5.5.0 的 `options` setter 對不同鍵有不同行為（有些會觸發 `reset()`）。

**怎麼量的：** 同一支 probe。寫入 200 行、`scrollToLine(120)`、
再 `write("$ half-typed-command")`（不含換行，模擬使用者打了一半還沒送出的輸入），
拍一張截圖，賦值 `options.theme`，等 400ms，再拍一張並重讀狀態。

### 實測（chromium 1228）

| 欄位 | 賦值前 | 賦值後 |
|---|---|---|
| `buffer.active.length` | 201 | 201 |
| `buffer.active.viewportY`（捲動位置） | 120 | 120 |
| `buffer.active.cursorX`（未送出輸入的長度） | 20 | 20 |
| `terminal.rows` | 35 | 35 |
| buffer 最後一行 | `$ half-typed-command` | `$ half-typed-command` |
| `.xterm-viewport` 背景 | `rgb(0, 0, 0)` | `rgb(240, 234, 214)` |
| 渲染出來的像素有沒有變 | — | **有** |

**判定：PASS。** 四項狀態全部不變，而終端確實重繪了。
`02-…md` §8 的「`terminal.options.theme = …`，不是 `new Terminal()`」可以照寫，
ADR 0027 那條斷言成立。

### 一個寫錯又修掉的判定

第一次跑的判定是「`.xterm-screen` 的 computed background 有沒有變」，
結果是 `rgba(0, 0, 0, 0)` → `rgba(0, 0, 0, 0)`，被判成 INCONCLUSIVE。
**那是判定寫錯，不是 xterm 有問題**：xterm 的背景由 renderer 畫，
不是那個元素的 CSS 背景。改成讀 `.xterm-viewport` 並加上截圖的位元組比對之後才是真的。

記在這裡是因為它是一個會重犯的錯：`VR-11` 的 E2E 若要斷言「主題真的換了」，
不能讀 `.xterm-screen` 的背景色。

## 3. FOUC 與 `theme-boot.js`

**要量什麼：** 設 `localStorage.cliora-theme = "porcelain"`，在 OS 為深色的環境下載入，
以 Playwright 在 `domcontentloaded` 與 `load` 各取 `<body>` 的 computed background；
另外在 CSP 生效的環境（`deploy/nginx`）確認 console 沒有 CSP violation。

**判準：** 兩次背景色相同，且沒有 CSP violation。
若外部檔仍然來不及（例如被 preload 排在 CSS 之後），
替代方案是把 `theme-boot.js` 以 `<script>` 放在 `<head>` 的**第一個**元素，
或改用 CSS-only 的 `prefers-color-scheme` 預設並接受「明示選擇與 OS 相反時閃一次」——
後者要寫進已知限制，不是靜默接受。

## 4. Lucide 的 bundle 增量

**要量什麼：** 目前 Lucide 只在四個檔案用了六個圖示。本期新增約十二個。
量 `npm run build` 前後 `dist/assets/*.js` 的 gzip 總大小，
並確認 tree-shaking 有效（不是整包進來）。

**判準：** 沒有硬門檻。若增量 > 20 kB gzip，代表 tree-shaking 沒生效，
要改成逐一具名 import（`import { Server } from "lucide-vue-next"` 已經是具名，
所以真出現這種情況要查 Vite 設定而不是改寫法）。同時記錄移除 `naive-ui` 的淨減。

## 5. ANSI 十六色在真實 Claude／Codex 畫面上

**要量什麼：** 用提案的十六色（`02-…md` §8）跑一次真實 session，
截下 Claude 的審批畫面、Codex 的 diff 輸出、`ls --color`、`git status`、
一個有 warning 的建置輸出。目視比對可辨識度。

**判準：** 任一畫面變得比 xterm 預設難辨識 → **退回預設，只覆寫 `blue` 與 `magenta`**
（那兩格是唯一低於 3:1 而且真的會被當前景用的）。
這是唯一一項**必須看真的畫面**的量測，因為它的判準是「使用者看得懂嗎」，
而那個問題沒有數字答案。

## 6. Monaco `setTheme` 的副作用

**要量什麼：** 開一個長檔案、捲到中間、折疊幾個區塊、用 find 搜尋一個字，
然後 `monaco.editor.setTheme()`。比對捲動位置、折疊狀態、find 的命中標記。

**判準：** 三者不變 → 通過。若折疊狀態會掉，記錄為已知限制
（預覽是唯讀的，折疊掉了不會失去工作），不擋票。
