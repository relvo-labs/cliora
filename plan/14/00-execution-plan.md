# 00 — 執行總控（工作區檔案編輯：建立、編輯、更名、刪除）

Ticket 前綴 `WE-`（**W**orkspace **E**diting）。

## 1. 成功定義

**要交付的：** 使用者在瀏覽器裡完成一輪完整的工作 —— 開檔、改內容、存檔、建立新檔、
改名、刪掉不要的 —— 全程不需要切到終端機打 `vim`／`mv`／`rm`。

**不得弄壞的六件事：**

1. **`os.Root` 的封閉性。** 四條新的寫入路徑（write／mkdir／rename／delete）與既有的讀取面、
   圖片投放面共用同一個 `workspace.Root`（ADR 0014、`SEC-001`、ADR 0024 W1）。
   `daemon/` 底下不得出現任何吃工作區絕對路徑的 `os.WriteFile`／`os.Create`／`os.Remove`／
   `os.Rename`。**這一條的地位又升了一級**：圖片投放繞過它是多寫一個檔案，
   編輯繞過它是覆寫或刪掉使用者既有的檔案。
2. **沒有無條件的破壞性操作。** wire 上會破壞或取代東西的三個請求型別都帶**必填**的
   `precondition`；不存在 `force`、`overwrite`、`recursive` 欄位（D2）。
   `mkdir` 沒有 precondition，因為它在 syscall 層就不可能覆蓋任何東西。
3. **平台不寫入它自己不肯顯示的內容，也不寫入它自己不肯讀取的位置。**
   寫入內容過 `Classify()`、寫入位置過 `SensitiveClassification()` —— 與讀取面**同一個函式**（D4）。
   這同時回答 ADR 0024 §4 留下的問題「敏感檔案政策是否適用於寫入方向」。
4. **未修改的儲存必須是位元組相同的儲存。** 換行字元、BOM、有沒有結尾換行、
   行尾空白，一個位元組都不能被編輯器偷改（D15、`FR-FILE-010.AC-04`）。
5. **每一個被覆寫或刪除的版本都還在。** 7 天的回收桶是刪除功能能出貨的前提（D6、D21），
   而且對目錄同樣成立 —— 刪一個資料夾是把整棵子樹搬進回收桶，還原是把它搬回來。
6. **這不是 Web IDE。** 產品非目標裡的那一條還在，只是線移動了 —— 新的線在哪裡由 D1 定義，
   並且要寫進 `.agent/skills/cliora-project-context`。

成功的判準是這十四項，每一項都要有可貼上的輸出（`06-…md` §3）：

1. 開一個 `.py` 檔、改一行、`Ctrl+S`，節點上的檔案內容改變，`git diff` 只有那一行。
2. **不改任何東西**直接存檔，節點上該檔的 SHA256 與存檔前**完全相同** ——
   對 CRLF 檔、沒有結尾換行的檔、帶 BOM 的檔、tab 縮排的檔各驗一次。
3. 對一個 `chmod 755` 的 shell script 存檔，存完之後它還是 755。
4. 在瀏覽器裡把檔案改到一半，同時在終端機上用 `sed -i` 改同一個檔，然後按存檔 ——
   得到 412 與「檔案已在節點上被修改」，節點上的檔案是 `sed` 的版本，**不是**瀏覽器的版本。
5. 建立 `docs/new/note.md`（父目錄不存在），檔案樹出現該檔；再建一次同名檔得到 409。
6. 更名一個檔案到另一個目錄，來源不存在、目的地存在且內容相同；目的地已存在時得到 409。
7. 刪除一個檔案，檔案樹裡它消失、`.cliora/trash/<今天>/` 出現一個帶原檔名的檔案，
   內容相同；把它 rename 回原位就是還原。
8. **建立一個資料夾、把它更名、在裡面放兩個檔案、再刪掉整個資料夾** ——
   trash 裡出現一個同名目錄且**兩個檔案都在裡面、路徑結構完整**；
   把該目錄 rename 回原位，兩個檔案連同內容與權限一起回來。
9. **對一個含有 `.git`（submodule 形式）的資料夾按刪除**，得到
   `FILE_DIRECTORY_CONTAINS_PROTECTED` 且**節點上一個位元組都沒有動**；更名同理。
10. 8 天前的 trash 檔案與目錄在下一次清理後消失；`.cliora/.gitignore` 沒有被刪。
11. Viewer 看不到任何編輯入口，且直接呼叫五個端點都得到 403，`authz.denied` 各留一筆。
12. 對 `.env`、`.git/config`、`node_modules/x.js`、一個指向工作區外的 symlink、
    以及**工作區根目錄本身**分別嘗試每一個動詞，全部被拒且
    **節點上沒有任何檔案或目錄被建立、改變或刪除**。
13. 送一段含 NUL 的內容，得到 `FILE_CONTENT_NOT_TEXT`，節點上該檔未被改動。
14. 關閉 `filesystem.editing.enabled` 的節點回報 `file_editing: false`，
    UI **不顯示**編輯與檔案樹的四個動詞（而不是顯示按了會失敗的按鈕）。

## 2. 範圍

### 納入

- `WE-01` 六項行為實測（`08-…md`），其中第 1 與第 6 項是**閘門**。
- `WE-02` ADR 0025、ADR 0024／0015 修訂、PRD 修訂（`FR-FILE-010`、`FR-FILE-011`、
  `NFR-005.AC-142` 二次改寫、`NFR-005.AC-109` 再收窄、`FR-FILE-002` 加註）、traceability 註冊。
- daemon：`workspace.Root` 的寫入方法補齊、
  `files/write.go`（write／mkdir／rename／delete 四個動詞的 default-deny 順序）、
  寫入方向的政策與**目錄的有界子樹走訪**（D22）、`revision`（檔案與目錄兩種）計算（`WE-03`）；
  回收桶、配額、清理、設定、`doctor`（`WE-04`）。
- 契約 v1.9.0（compatible）：四對型別、`filesystem.content` 與 `filesystem.entries`
  各新增 `revision`、`node-register.file_editing`、共用的 `precondition` 定義、
  十個 golden fixture（`WE-05`）。
- Central：五個 HTTP 端點、RBAC action `file.write`、四個稽核事件、
  十三個錯誤碼、`can_edit_files` 能力旗標、migration `0020`／`0021`（`WE-06`）。
- 前端：Monaco 編輯模式與存檔（`WE-07`）、檔案樹的四個動詞與確認流程（`WE-08`）、
  「唯讀」敘事的第二次修正與 trash 在檔案樹的呈現（`WE-09`）。
- `.agent/skills` 修訂（`WE-10`）、evidence／gates／runbook／release note（`WE-11`）、
  安全審查與 exit gate（`WE-12`）。

### 不納入

- **超過 `max_directory_entries`（20000 項）的目錄更名與刪除。** 見 D22。
  這不是「不做」，是「這種規模的操作屬於終端機」，而且會給出明確的錯誤碼。
- **多檔未存緩衝、分頁列。** 見 D13。
- **三方合併、衝突解決 UI、diff 檢視。** 見 D14。
- **自動儲存。** 見 D12。
- **一般檔案上傳與下載。** `NFR-005.AC-109` 這一期再被切下一片，仍不是被撤銷。
- **非 UTF-8 檔案的編輯。** 讀不到就編不了，這是自然結果不是額外限制（D4）。
- **超過 `max_preview_size` 的檔案。** 同上，而且兩個上限**必須相等**（D11）。
- **git 操作**（stage／commit／branch）。產品非目標，且 D1 的線就畫在這裡。
- **回收桶的 UI 還原按鈕。** 還原＝把檔案 rename 出來，不是新動詞（D7）。

## 3. 固定基線決策

| # | 決策 | 選擇 | 理由 |
|---|---|---|---|
| D0 | **本期的風險長什麼樣** | 本期**不新增能力，只新增介面**。持有 `file.write` 的兩個角色（Admin、Developer）今天就同時持有 `terminal.operate`，在同一台節點的同一個工作區上可以 `rm -rf`；在 ADR 0023 的節點上 codex 還是無沙箱執行的。所以本期的威脅模型不是「使用者變得可以刪檔」，而是「刪檔變得只要誤點一次」。**所有防護因此朝向誤操作**：版本前提、回收桶、確認、稽核。越權那一側由既有的 RBAC 與 `os.Root` 承接，本期不放鬆任何一格 | 這條放第一，因為它決定了下面每一條的取捨方向。把它寫反（「這是一個危險的新權限」）會導出一個沒人用的功能：預設關閉、層層確認、每次操作都要重新驗證身分。把它寫掉（「反正都能 rm 了」）則會導出沒有回收桶、沒有版本前提的實作。**兩個錯誤方向都很好走，所以要先把方向釘住** |
| D1 | **這是不是 Web IDE** | 交付：單一檔案的編輯、顯式儲存、建立／更名／刪除、版本衝突偵測。**不交付**：多檔未存緩衝、分頁列、跨檔重構、內建 git、LSP／自動完成／定義跳轉、建置任務、編輯器內嵌終端機。線的判準寫成一句可以貼進 skill 的話：**「一次一個檔案，一次一個明確的動作，每一個動作在節點上都是一個 syscall。」** | `.agent/skills/cliora-project-context` 目前寫著「Do not introduce … a Web IDE … without a requirements change」。本期**就是**那個 requirements change，所以它有義務說出新的線在哪裡 —— 否則下一個人只會看到禁令被打破過一次，而不知道打破到哪裡為止。這條線不是保守，是把「編輯器」與「開發環境」分開：前者可以用一句話描述它對節點做了什麼，後者不行 |
| D2 | **wire 的形狀** | **會破壞或取代東西的三個型別**（`filesystem.write`／`rename`／`delete`）各帶**必填**的 `precondition`：`{"absent": true}` 或 `{"revision": "sha256:<64 hex>"}`。**沒有** `force`、`overwrite`、`recursive`、`if_exists` 這類欄位，`additionalProperties: false`。第四個型別 `filesystem.mkdir` **沒有** `precondition`，而且送了會被拒 —— `mkdir(2)` 在 syscall 層就不可能覆蓋任何東西，替它發明一個只有一種合法值的欄位是雜訊 | 1.4.0／1.6.0／1.7.0／1.8.0 是同一條規矩的四個版本：**不讓對面決定它不該決定的事**。上一期守的是「請求端不得命名檔案」，而 ADR 0024 §4 已經寫明**那一條不能沿用到編輯**（編輯的本質就是指名某一個檔案）。所以本期換一個守法：**請求端必須說出它以為自己在動哪一個版本。** 它擋掉的是同一類問題的另一半 —— 不是「你不知道你在寫哪裡」，而是「你不知道那裡現在是什麼」。這條可以被一個 gate 檢查（`GATE-WE-NO-UNCONDITIONAL-WRITE`），註解不行 |
| D3 | **版本識別是什麼** | **檔案**：內容的 SHA-256。**目錄**：其**直屬**項目的 `name\ttype` 排序後串接的 SHA-256。兩者格式相同（`sha256:<64 小寫 hex>`），分別由 `filesystem.content` 與 `filesystem.entries` 隨每一次成功讀取／列表回傳 | 目錄也給 revision，是為了讓 D2 的 precondition 維持**只有兩種形狀**，不必為目錄發明第三種。它的語意是「我要動的是我上次看到的那個目錄」，而那正是遞迴刪除最需要的保護：有人在你沒看的時候往裡面放了東西，刪除就會被擋下來。副作用是**你不能刪除一個你沒有打開過的資料夾**（前端要先 list 一次）—— 那是對的。**已知限制要寫下來**：它只涵蓋直屬層，深處新增的檔案不會讓它失效，真正列舉整棵子樹的是 D22 的走訪。**被否決**：`mtime`＋`size`（格式化工具會在同一秒寫回同樣長度的內容，這正是最需要被擋住的情境）；`inode`＋`mtime`（本期的寫入是 temp＋rename，**每次都會換 inode**，用它當版本會讓自己的下一次存檔永遠不符）；目錄用遞迴雜湊（CLI 在跑的時候幾乎永遠不符，等於把刪除變成不可用）。SHA-256 對 2 MiB 的成本要量（`08-…md` §5）並計入 ADR 0015 的 3 秒預覽預算 |
| D4 | **可寫的邊界＝可讀的邊界** | 寫入的**內容**必須通過 `files.Classify()` 且結果為 `VerdictText`；寫入的**位置**（含 rename 的來源與目的地）必須通過 `policy.SensitiveClassification()` 且結果為空。兩者都是讀取面**正在用的同一個函式**，不是另一份複製 | 一句話：**平台不寫入它自己不肯顯示的內容，也不寫入它自己不肯讀取的位置。** 這同時做完三件事：(a) 回答 ADR 0024 §4 明確留給編輯的問題；(b) 讓「使用者寫了一個自己再也打不開的檔案」不可能發生；(c) 讓敏感檔案政策不需要第二份實作 —— 有第二份就會有第二天，兩份就會分岔。**被否決**：寫入方向用比較寬的規則（「反正是他自己的檔案」）—— 那會允許前端建立一個 `.env`，而那個檔案接下來會被平台自己拒絕顯示，是一個平台親手製造的黑洞 |
| D5 | **原子性與權限** | temp（`.<name>.part`，0600）→ 寫入 → `fsync` → **以 temp 檔自己的 fd 呼叫 `f.Chmod` 複製原檔權限** → rename 就位 | 用 fd 的 `Chmod` 而不是 `Root.Chmod(path)`，是因為 Go 自己的文件記載 `Root.Chmod` 在 Unix 上對「操作進行中被換成 symlink」有 race。這不是防禦性寫法，是照著上游的警告寫。**複製權限這一步不能省**：在瀏覽器上改一行 `deploy.sh`，存完之後它不能執行了 —— 這種 bug 會被回報成「平台弄壞了我的腳本」，而且是對的。**被否決**：就地 `O_TRUNC` 寫入（保住 inode、hardlink 與權限，但寫到一半失敗就是資料損毀，而這條路徑沒有 undo）。代價要寫進 ADR：rename-over 會換 inode，所以既有的 hardlink 會斷、CLI 已經開著的 fd 會看到舊內容 |
| D6 | **回收桶** | `.cliora/trash/<UTC 日期>/<ULID>-<原名>`，保留 7 天。**刪除＝把目標 rename 進 trash**（檔案與目錄同一條路徑，一個 syscall，O(1)，不複製位元組，整棵子樹一起搬）；**覆寫＝把舊版本 `Link` 進 trash ＋ rename 新檔就位**（覆寫需要原檔在寫入期間留在原位，所以用 hardlink 而不是 rename） | 這條同時解掉兩件事。**第一**，ADR 0024 的 W2 要求「單次大小、累計配額、保留期三者齊備」，而編輯本身沒有東西會過期 —— **被覆寫掉的那個版本才有**。沒有回收桶，W2 對編輯只成立三分之二，而 `docs/security-review-p13.md` 第 8 題已經把這件事點名留給本期。**第二**，ADR 0024 把 undo 列為編輯必須決定的事，這就是答案。**兩個動詞用兩個 syscall 是刻意的**：delete 用 rename 因為它同時適用於目錄、而且沒有中間狀態；overwrite 用 link 因為原檔必須在新內容就位之前一直在原位。失敗階梯：EXDEV／不支援時，檔案 ≤ `trash.max_copy_bytes` 改用複製，**目錄一律拒絕**（複製一棵樹是無界的），回 `FILE_TRASH_UNAVAILABLE` —— 寧可拒絕刪除，也不做沒有備份的刪除 |
| D7 | **還原不是新動詞** | 把檔案或目錄從 `.cliora/trash/` **rename 出來**就是還原，整棵子樹一次回來。因此 `.cliora/` 的寫入禁令要開一個**寫死的**例外：`from` 在 `.cliora/trash/` 之下、`to` 不在 `.cliora/` 之下的 rename 允許，其餘一律拒絕 | 少一個動詞、少一個端點、少一個權限、少一份測試。因為刪除是 rename 進去的，還原就是同一個 syscall 反過來 —— **目錄的還原不需要重建任何結構**。代價是一個必須寫死並被測試釘住的例外，而例外本身要在程式碼裡有註解說明它為什麼存在 |
| D8 | **目錄與檔案同樣可以建立、更名、刪除**（2026-08-02 使用者指示） | 新增第四個動詞 `filesystem.mkdir`；`rename` 與 `delete` 同時適用於兩種型別。**刪除一個目錄＝連同其全部內容一起移進回收桶**，還原時整棵回來。建立檔案時仍然隱含補齊父目錄 | 使用者要的是「一次性完成所有工作」，而「要新增資料夾請去開終端機」正面違反那句話。原本排除目錄的三個理由，兩個在改用 rename 進回收桶（D6）之後消失了：整棵子樹一個 syscall 就搬得走，還原也一樣；空目錄在 git 裡表達不出來這件事仍然為真，但那是使用者的問題不是平台的。**剩下的那個理由是真的**，所以它變成 D22 —— 目錄操作會一次動到無界的東西 |
| D22 | **目錄操作＝對其中每一項套用同一個判斷** | 目錄的 **rename 與 delete** 都要先做一次**有上限的子樹走訪**：(a) 其中任何一項被寫入政策拒絕（`.git`、`.cliora`、敏感檔案、排除目錄），整個操作拒絕，回 `FILE_DIRECTORY_CONTAINS_PROTECTED` 並指出第一個；(b) 項目數超過 `max_directory_entries`（預設 20000）拒絕，回 `FILE_DIRECTORY_TOO_LARGE`；(c) 刪除時子樹總位元組數要計入回收桶配額。**不得部分執行** —— 走訪通過才動手，動手就是一個 rename | 沒有這一條，遞迴刪除會**繞過本期每一條逐檔保護**：刪掉一個含有 submodule 的資料夾，就等於把 `.git` 搬進回收桶，而 D4 花了整整一條規矩在擋那個檔案。一句話：**目錄操作是把同一個操作套用到裡面的每一樣東西，所以它必須被同樣地判斷。** 更名也要走訪（而不是只有刪除），因為把一個含 `.env` 的資料夾搬出 `.gitignore` 涵蓋範圍，與直接動那個 `.env` 是同一件事。代價是超過兩萬項的資料夾不能在瀏覽器上更名 —— 那是對的，那種操作屬於終端機 |
| D9 | **誰可以編輯** | 一個新 RBAC action **`file.write`**，Admin＋Developer 持有，Viewer **不**持有。**不要求 writer 角色** | **被否決**：拆成 `file.edit`／`file.delete` 兩個 action（三個固定角色底下沒有人能組出「可改不可刪」，而 permission matrix 有三重自動檢查，每多一個 action 就多三處要維護）；沿用 `file.upload`（那條的語意是「把一團位元組交給 CLI」，稽核上會分不出「丟了張圖」與「刪了個檔」）；沿用 `file.browse`（Viewer 持有）。**不要求 writer 角色**是刻意的：single-writer 是**終端機**的語意（誰現在可以打字），不是工作區的語意。兩個人同時編輯不同檔案沒有問題；同時編輯同一個檔案由 D3 的版本前提處理 |
| D10 | **節點可以拒絕**（W4） | daemon 設定 `filesystem.editing.enabled`（預設 **`true`**），以 `node-register.file_editing` 回報；UI 依回報決定是否顯示入口 | 預設 `true` 的理由就是 D0：本期不新增能力。反過來說，預設 `false` 的代價是這個功能在每一台既有節點上都是隱形的，而會去改那個設定的人通常就是要這個功能的人。沿用 1.7.0 的 report-only 形狀。與 ADR 0023 D2、ADR 0024 D8 相同，**升級即取得新行為**，所以同樣要有 release note 與 runbook，不得靜默 |
| D11 | **上限** | 單次寫入上限＝`filesystem.max_preview_size`（2 MiB），**兩者必須相等，且由一個測試斷言相等**。每日寫入次數 2000。trash 累計 64 MiB／session（超過先清最舊，仍超過才拒絕）。目錄操作的走訪上限 20000 項（D22） | 兩個上限不相等的那一天，使用者會建立一個自己再也打不開的檔案（寫入上限較大）或存不回一個剛剛才讀進來的檔案（讀取上限較大）。這不是需要判斷的取捨，是一條要被測試釘住的等式。每日次數是為了擋住一個壞掉的客戶端把節點的 IO 佔滿 —— 顯式儲存（D12）之下，2000 次遠高於任何人手動存檔的量 |
| D12 | **不自動儲存** | 只有 `Ctrl+S` 與明確的「儲存」按鈕會寫入節點 | 兩個理由。**稽核**：W3 要求每次寫入留紀錄，自動儲存會讓稽核表長出使用者沒有意識到自己做過的事，而「誰改了這個檔案」的答案就變成一串時間戳。**節點**：一個會自己寫檔的瀏覽器分頁，對正在同一個工作區跑 watcher／build 的 CLI 是持續的雜訊來源 —— 而 CLI 正在跑，本來就是這個產品最常見的狀態 |
| D13 | **一次只能有一個未儲存的檔案** | 切換到別的檔案、切換 session、離開頁面之前，必須先儲存或明確捨棄 | **被否決**：多檔緩衝。它需要分頁列，而分頁列就在 D1 那條線的另一邊；更要命的是 `useMonacoModel` 目前的 LRU（上限 8）在第 9 個檔案時會 dispose 最舊的 model —— 多檔緩衝會讓它變成「**悄悄丟掉你沒存的東西**」。單一 dirty 檔案讓這個問題不存在，而不是讓它被一段 eviction 的例外邏輯管著 |
| D14 | **衝突不做合併** | 版本不符時給兩條路：「重新載入（放棄我的修改）」與「另存為新檔」。後者就是 `precondition: absent` 的建立，不是新功能 | **被否決**：三方合併（要有共同祖先，而我們手上只有兩個版本）；自動重試（那就是無條件覆寫，正面違反 D2）；顯示 diff（要在瀏覽器裡做 diff 演算法與 diff UI，而使用者在這個當下真正需要的資訊只有一句「節點上的版本比較新」）。**這一條要誠實寫進 release note**：CLI 一直在改檔案，所以版本不符不是例外情境，是日常 |
| D15 | **編輯器不得偷改內容** | `trimAutoWhitespace: false`、不插入結尾換行、EOL 沿用原檔偵測值、`detectIndentation` 只影響新輸入、BOM 原樣保留、`renderFinalNewline` 不改變模型 | 每一項都對應一種「平台弄壞了我的檔案」的回報。這一條**不靠設定清單保證**，靠 `FR-FILE-010.AC-04` 那條測試保證：讀進來、不改、存回去，SHA256 必須相同 —— 對 CRLF、無結尾換行、BOM、tab 縮排、行尾有空白的五種檔案各驗一次。設定清單會被下一個人動，測試不會 |
| D16 | **Central 不落地** | 請求體讀進記憶體（上限 2 MiB）、轉發、丟棄。不寫暫存檔、不寫 DB、不進 log、不進 metrics label。稽核只記路徑、位元組數與前後版本識別 | 與 ADR 0024 §5 相同的理由，而且更硬：圖片是使用者自己剛剛選的檔案，編輯的內容是使用者的**原始碼** |
| D17 | **HTTP 的前提怎麼表達** | `If-None-Match: *`（建立）與 `If-Match: "sha256:…"`（覆寫、更名、刪除）。缺少前提回 **428**，不符回 **412** | **被否決**：把 precondition 塞進 request body（`DELETE` 帶 body 在部分代理與 client 上會被丟掉，而且這正是 `If-Match` 存在的理由）；用 query string 帶 revision（可行但會讓 revision 進到 access log 與瀏覽器歷史，沒有必要）。**選這個還有一個副作用是好的**：428／412 是標準語意，審查的人不必先讀我們的錯誤碼表才知道發生什麼事 |
| D18 | **稽核記相對路徑** | 四個新事件 `file.create`／`file.edit`／`file.rename`／`file.delete`，metadata 記工作區相對路徑、位元組數、前後 revision。**不記內容** | 與 `file.sensitive_read_denied` 只記分類的做法**不同**，理由要寫在 ADR 裡：那一條是**否決**，記路徑等於在 Central 的資料庫裡留下一個使用者看不到的檔案的存在證明；這一條是使用者本來就看得到、而且是他自己動的。不記路徑的話，W3 要回答的「誰改了這個檔案」就只剩一個計數器 |
| D19 | **「唯讀」的第二次改寫** | `NFR-005.AC-142` 昨天（2026-08-01）才因為 ADR 0024 改寫過，今天要再改一次；`FR-FILE-002.AC-01`（Monaco 唯讀顯示）**文字不動**，改為加註「預覽預設唯讀；編輯是顯式切換的另一個模式，見 `FR-FILE-010`」 | 一條核心原則在 24 小時內被改兩次，這件事本身要寫進 ADR 0025 的 Context —— 它是「寫姿態而不是寫現況」這個做法**有效**的證據：ADR 0024 立下的 W1–W4 今天原封不動可以套用，被推翻的只有那句描述現況的話。AC-01 文字不動的理由沿用 p13 §2.1：改 AC 文字會讓 traceability 的既有連結全部要重驗，而本期真正新增的是一個模式，那應該是新需求 |
| D20 | **這一期不碰的東西** | terminal relay 與 single-writer、ws-ticket、backpressure、tunnel、daemon update、edge nginx、CSP、圖片投放的既有行為、檔名搜尋、文字判定 | 判準：若 diff 出現在 `backend/app/api/ws/terminal.py`、`deploy/`、`daemon/internal/tunnel/`、`daemon/internal/update/`，或 `files/policy.go` 的 `Classify()` **函式本體**（新增呼叫端不算），就是走錯路了 |
| D21 | **出貨順序有一條硬性依賴** | 編輯（`FR-FILE-010`）與建立／更名／刪除（`FR-FILE-011`）可以分開出貨，但**刪除不得早於回收桶**（`WE-04`）。若 `WE-04` 落後，`WE-06` 要以設定關閉刪除端點出貨，而不是先出無安全網的刪除 | D0 說本期的威脅是誤操作，D6 說回收桶是刪除的安全網。先出刪除再補回收桶，中間那段時間的每一次誤刪都是不可回復的，而「之後會補」不會讓已經消失的檔案回來 |

**閘門仍然存在**：`WE-02a` 未核准前不得動 daemon 程式碼。理由與前兩期相同 ——
這是一次姿態的**具體化**（ADR 0024 立了 W1–W4，本期要證明它們真的能承接第二條路徑），
書面決定必須先於實作。

`WE-01` 的六項裡只有兩項是閘門：

- **第 1 項（`os.Root.Link` 的語意）** 是 D6 的前提。Link 若不會在目的地已存在時失敗，
  或在目標檔案系統上不可用，回收桶就要改設計（複製或拒絕），那是設計變更不是參數調整。
- **第 6 項（worktree 的 `.git` 是檔案不是目錄）** 是 D4 的前提。
  `SensitiveClassification` 目前用 `denied_directories` 比對**路徑片段**，
  在 git worktree 裡 `.git` 是一個內容為 `gitdir: …` 的**檔案** ——
  它會通過目錄規則，然後被當成一般文字檔編輯，而改掉它等於把整個 worktree 指到別的地方。
  這一項不成立的話 `FR-FILE-011.AC-06` 要重寫。

其餘四項（Monaco 往返、watcher 行為、誤擋率、SHA-256 成本）不擋任何票，
但會決定 D15 的設定清單、release note 的措辭與 `FR-FILE-010.AC-04` 的驗收檔案集合。

## 5. 風險

| 風險 | 徵狀 | 處置 |
|---|---|---|
| **使用者從瀏覽器刪掉了不該刪的東西** | 「我的檔案不見了」 | D6 的回收桶（7 天）＋ D7 的還原路徑＋刪除確認要顯示檔名與大小＋稽核。runbook 要寫「使用者說檔案不見了」的第一步就是去 `.cliora/trash/` |
| **刪一個資料夾＝一次刪掉幾百個檔案**（本期單一操作後果最大的一件事） | 「整個 `src/` 不見了」 | 四層：D3 的目錄 revision（沒打開過就刪不掉、內容變了就擋下來）、D22 的走訪（含受保護項目就整個拒絕）、D6 的整棵子樹進回收桶（一次 rename 就能還原）、以及刪除確認要顯示直屬項目數。**這四層都不是可選的**，少任何一層這個動詞就不該出貨 |
| **遞迴刪除繞過逐檔保護** | 刪掉含 submodule 的資料夾，`.git` 被搬進回收桶 | D22 的走訪就是為了這件事。`GATE-WE-WRITE-POLICY` 要包含「目錄含受保護項目時整個拒絕」這一格 |
| **編輯器偷改了整個檔案** | 只改一行，`git diff` 卻是整檔（CRLF 變 LF、結尾多一個換行、行尾空白被吃掉） | D15＋`FR-FILE-010.AC-04` 的五種檔案往返測試。這是本期**最可能發生**的失敗，因為它不會噴錯，只會在 code review 時被別人看到 |
| **與 CLI 的寫入互相蓋掉** | 使用者存檔，CLI 剛寫過的內容不見了 | D3 的版本前提是主要防線；D14 的兩條路是使用者面的處置。**要量的是頻率**（`WE-01` 第 3 項）：如果 CLI 在跑的時候版本不符是常態，UI 的措辭要從「錯誤」改成「情況」 |
| **rename-over 換掉 inode，弄壞正在跑的東西** | watcher 沒有觸發、CLI 讀到舊內容、hardlink 斷開 | `WE-01` 第 3 項先量。無論結果如何都要寫進 release note；若 watcher 真的漏事件，那是 D5 的已知代價而不是 bug，但使用者必須先知道 |
| **`.git/` 或 worktree 的 `.git` 檔案被改** | repo 損毀，而且是最不該損毀的那一種 —— 使用者的 undo 本身 | D4＋`FR-FILE-011.AC-06`；`WE-01` 第 6 項是閘門；`GATE-WE-WRITE-POLICY` 要同時測目錄形式與檔案形式 |
| **回收桶把磁碟吃光** | 節點磁碟滿，session 起不來 | D11 的 64 MiB／session＋7 天清理＋超額先清最舊；`doctor` 增加一行 trash 大小；runbook 寫如何手動清空 |
| **敏感規則在寫入方向擋得太寬** | 使用者編不了 `secrets.test.ts`、`credentials.md` 這類名字裡有關鍵字的一般檔案 | `WE-01` 第 4 項先量本 repo 的誤擋數。注意這**不是回歸**（那些檔案今天也讀不到），但編輯會讓它變得刺眼。若數量大，處置是調整 `denied_patterns` 的預設值（那是 `FR-FILE-005` 的既有授權「系統應允許管理員調整規則」），**不是**在寫入方向放寬（那會讓 D4 的對稱性破掉） |
| **「一次一個 dirty 檔案」被使用者視為缺陷** | 「為什麼我不能同時改兩個檔案」 | D13 是刻意的。UI 要把它講成規則而不是錯誤：切換檔案時直接問「儲存／捨棄／取消」，不要只是擋住 |
| **本期把產品變成 IDE** | 下一個 PR 要求分頁列、再下一個要求 git 面板 | D1 的線寫進 `.agent/skills/cliora-project-context`，讓它在下一次被引用時就出現 |
