# Cliora 工作區檔案編輯：建立、編輯、更名、刪除

本目錄交付 2026-08-02 由使用者指示的一件事，ticket 統一使用 `WE-` 前綴
（**W**orkspace **E**diting）：

> 目前已經實際驗證過平台基本功能無問題，此階段我要解放工作檯的前端編輯功能，
> 在前端要可以 create/edit/rename/delete 檔案，
> 以達到可以直接在系統前端一次性完成所有工作的效果

> （2026-08-02 追加）目錄也要可以 create/delete/rename

這是 ADR 0024 在**前一天**明白預告的那一期。它當時撤銷了唯讀姿態、
立下每一條寫入路徑都要滿足的 W1–W4、交付了第一條路徑（圖片投放），
並寫下編輯必須自己決定的五件事：衝突處理、並行寫入、敏感檔案政策在寫入方向是否適用、
`.git/` 的保護、undo。**本期就是那五件事的答案**，加上它特意留下的那條界線 ——
「請求端不得命名檔案」不能沿用到編輯，因為編輯的本質就是指名某一個檔案。

## 這一期真正的形狀

上一期守的是「**你不能決定寫到哪裡**」。這一期做不到那件事（客戶端必須指名），
所以換一條規矩守：

```
              ADR 0024（圖片投放）              ADR 0025（本期）
              ─────────────────                ────────────────
  守什麼      請求端不得命名檔案                請求端必須說出它以為
                                                自己在動哪一個版本
  wire        沒有 filename／path／            precondition 必填，只有
              directory／extension              {absent} 與 {revision} 兩種
                                                （mkdir 沒有前提：它不可能覆蓋東西）
  一次消滅    路徑穿越、雙副檔名、覆寫          覆寫別人剛寫的、刪掉已經
                                                被換掉的、蓋在新出現的同名檔上
  共同點      關掉入口，就沒有驗證程式碼會寫錯
```

而位置與內容的邊界不需要新發明 —— 直接用讀取面**同一個函式**：

```
          讀取                          寫入
    ┌──────────────────┐        ┌──────────────────┐
    │ SensitiveClassif │◄──同一個──►│ 位置：兩端都要過  │
    │ Classify()       │◄──同一個──►│ 內容：必須是文字  │
    └──────────────────┘        └──────────────────┘
      平台不寫入它自己不肯顯示的內容，也不寫入它自己不肯讀取的位置
```

這一句同時回答 ADR 0024 的第三個問題，並且讓「使用者建立了一個自己再也打不開的檔案」
變成不可能。

## 目錄納進來之後，兩件事變了

使用者在計畫初稿之後追加「目錄也要可以 create/delete/rename」。
這不只是多三個入口，它改了兩個地方，而兩個都是往好的方向：

1. **回收桶從 hardlink 改成 rename。** 原本檔案的刪除是
   「link 進回收桶 ＋ unlink 原路徑」，但 `link(2)` 不能用在目錄上。
   改用 `rename` 之後，**檔案與目錄的刪除是同一行程式碼、一個 syscall、
   沒有中間狀態**，而刪一個資料夾就是整棵子樹一起搬進去 ——
   還原也只是把它 rename 回來，不需要重建任何結構。
   （覆寫仍然用 hardlink，因為原檔必須在新內容就位之前留在原位。）
2. **多了一條 W1 的延伸：目錄操作要對整棵子樹套用同一個判斷**（D22）。
   沒有它，遞迴刪除會繞過本期每一條逐檔保護 ——
   刪掉一個含 submodule 的資料夾，就等於把整份計畫花了一整條規矩去保護的
   `.git` 搬進回收桶。這是本期新增的第九道安全審查題。

**目錄沒有帶來第三種 precondition。** 目錄的 revision 是它直屬項目清單的雜湊，
所以「我要刪的是我上次看到的那個資料夾」與「我要覆寫的是我上次讀到的那個檔案」
是同一個欄位、同一個 412。副作用是**你不能刪除一個你沒有打開過的資料夾** ——
那是對的。

## 這一期最容易做錯的七件事

1. **讓編輯器偷改整個檔案。** 只改一行、`git diff` 卻是整檔 —— CRLF 變成 LF、
   結尾多一個換行、行尾空白被吃掉。這是本期**最可能發生**的失敗，
   因為它不噴任何錯誤，只會在別人 review 你的 PR 時被看到。
   防線不是那五項 Monaco 設定（設定會被下一個人動），是
   「不改就存＝位元組相同」那條測試（`00-…md` D15、`FR-FILE-010.AC-04`）。
2. **在 wire 上留一條無條件寫入的路。** 一個 `force: true`、一個「precondition 選填」，
   都會讓樂觀鎖退化成建議。`GATE-WE-NO-UNCONDITIONAL-WRITE` 守它，註解守不住。
3. **先出刪除、之後再補回收桶。** 中間那段時間的每一次誤刪都是不可回復的
   （`00-…md` D21）。**刪除資料夾還要多等一件事**：D22 的子樹走訪 ——
   它同時是安全防線與配額計算，兩者缺一都不能出貨。
4. **在寫入方向放寬敏感規則**，因為「反正是他自己的檔案」。那會讓前端能建立一個
   平台接下來自己拒絕顯示的 `.env` —— 一個平台親手製造的黑洞（D4）。
5. **忘記 git worktree 的 `.git` 是一個檔案。** 現行的規則比對路徑片段，
   擋得住 `.git/config`，擋不住那個檔案；而改掉它等於把整個 worktree 指到別的地方。
   這是本期兩個閘門之一（`08-…md` §6）。
6. **存檔時忘記把權限複製回去。** 在瀏覽器改一行 `deploy.sh`，
   存完之後它不能執行了 —— 這種 bug 會被回報成「平台弄壞了我的腳本」，而且是對的（D5）。
7. **把它做成 Web IDE。** 產品非目標裡的那一條還在，只是線移動了。
   新的線是：**一次一個目標，一次一個明確的動作，每一個動作在節點上都是一個 syscall。**
   本期有義務把它寫進 `.agent/skills/cliora-project-context`，
   否則下一個人只會看到禁令被打破過一次，而不知道打破到哪裡為止（D1）。

## 兩件本期順手補上的事

- **`.cliora/uploads/` 的圖片終於刪得掉了。** ADR 0024 的
  `FILE_UPLOAD_QUOTA_EXCEEDED` 錯誤訊息一直在叫使用者
  「請在檔案樹的 `.cliora/uploads/` 刪除不需要的圖片」，而在本期之前那件事做不到。
- **`docs/security-review-p13.md` 第 8 題有答案了。** 它把
  「W1–W4 是否真的可以承接下一條寫入路徑」列為待答，並點名 W2 對編輯只成立一半。
  答案是：**四條全部成立，W2 的第三腿需要回收桶才有意義** ——
  而回收桶不是為了滿足規矩發明的，它同時就是 ADR 0024 點名的 undo。

## 一件值得記下來的小事

`NFR-005.AC-142`（產品核心原則第 7 條）會在 **24 小時內被改第二次**。
ADR 0024 昨天把「檔案總覽第一階段採唯讀模式」改成「預覽為唯讀＋W1–W4」；

## 可以只做一半

編輯（`FR-FILE-010`）與建立、更名可以先出貨；**刪除檔案**要等回收桶（`WE-04`）；
**刪除資料夾**要等回收桶**與**子樹走訪（`WE-03b`）兩者都完整落地。
只能是這個順序，不能反過來（`00-…md` D21、D22、`06-…md` §6）。
