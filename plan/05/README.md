# Cliora P4 可實作規劃（管理、維運與上線強化）

本目錄把 `research/01` 的 **Phase 4（Operations & Hardening）** 轉成可直接建立 ticket、撰寫程式與驗收的執行規格。P4 是 **MVP 的最後一個 release gate**：它不再新增垂直功能，而是把 P0–P3 已交付的四條垂直（Terminal PoC、Node control plane、Session/Terminal、Workspace Files）收斂為**可營運**的產品——角色權限在 HTTP／browser WS／daemon WS／UI 四處一致且有 owner 範圍、重要操作可稽核且可查詢、Dashboard 顯示真實聚合並標示 freshness、metrics/alerts/runbook 可支撐 PRD 規模、daemon 可安全自我更新並回復、資料可備份還原、正式部署有 HTTPS/WSS 與 secret 注入，最後通過 **PRD 第 19 節 20 項 MVP 驗收條件**與 **tech §23 安全基準 15 項**。

P4 **不新增**任何新的資料面能力：不做檔案編輯／上傳／下載、任意 shell、Central SSH、Git automation、Terminal 全量保存或 session replay、多 agent orchestration、Kubernetes、message broker 或後端水平擴充（永久非目標，PRD §4／tech §24）。

> 命名說明：plan 資料夾編號比 research 的 Phase 編號多 1。`plan/01`=Phase 0（Terminal PoC）、`plan/02`=Phase 1（Node Control Plane）、`plan/03`=Phase 2（Session 與 Terminal）、`plan/04`=Phase 3（Workspace Files），皆已交付。本目錄 `plan/05` 對應 **Phase 4（管理、維運與上線強化）**，ticket 前綴為 `P4-`；research 內的 work package 仍以 `P4-W1`…`P4-W6` 稱之。

## 前置狀態（P0–P3 已交付，P4 直接沿用）

以下是實際 repo 現況，P4 的每張 ticket 都建立在它之上，**不假設任何規劃中的檔案已存在**。

- **RBAC 骨架已存在但未完整化**：`app/services/rbac.py` 已定義十個 action key（`node.view`、`session.create/view/terminate`、`terminal.operate/takeover`、`file.browse`、`enrollment.manage`、`node.manage`、`audit.view`），由 seed migration `0002`/`0006`/`0007` 綁定三角色。`app/api/http/deps.py` 的 `require_action()` 已套在 nodes/sessions/enrollment/files 端點，`app/api/ws/terminal.py` 已用 `has_action()` 決定 writer/takeover。**三個實際缺口**：(1) `audit.view` 已 seed 但**沒有任何 endpoint 使用它**；(2) 授權只看 role，**沒有資源範圍/owner 規則**——任何 Developer 可終止他人的 session、可 attach 任何 session；(3) permission matrix 沒有單一 source of truth，也沒有「每個 endpoint × 每個 message type × 三角色」的 allow/deny 矩陣測試。
- **Audit 寫入已存在但無法查詢**：`app/services/audit.py` 已有 P1（login/logout、enrollment、node register/disable/remove、credential revoke）、P2（session create/attach/takeover/terminate/failed）與 P3（`file.sensitive_read_denied`）共 17 個 action，並經 `redact_mapping()` 去敏。**缺口**：`AuditLog` 表有 `action`/`created_at`/`node_id` 索引但**沒有 `user_id` 索引**；metadata **沒有帶 `request_id`**（`app/logging.py` 的 `request_id_var` 只進 log 不進 audit）；`daemon.update` 事件尚不存在（SEC-006 清單要求）；**完全沒有 audit 查詢 API 與 Admin UI**。

## 使用規則

1. **先過 `P4-01`（決策 ADR）與 `P4-02`（protocol v1.4 凍結），且 `P4-03`（RBAC 完整化）通過授權 gate**，再並行 audit、Dashboard、observability、update 與部署。**RBAC 是 P4 的硬性 Gate**：在「每個 endpoint 與每個 WS message type × 三角色」的 allow/deny 矩陣測試全綠之前，不得新增任何對外端點（含 audit 查詢與 aggregates），否則新端點會在沒有授權基準的狀態下上線。
2. 修改契約的 PR 必須先於 consumer 合併，並同步 schema、`contracts/v1/fixtures/manifest.json`、fixtures 與 Python/Go/TS 三個 consumer。每項 task 都需提交其列出的產物與測試；「可手動展示」不能替代自動測試。**UI 隱藏不能替代 server authorization**：任何以 `v-if="auth.hasPermission(...)"` 隱藏的操作，都必須有對應的 server 端 403 測試。
3. 依 `.agent/skills/cliora-project-context`：先檢視 repo 現況、不假設規劃中的目錄已存在、做最小可行變更，並保全 trust-boundary invariants（outbound-only daemon WSS、Central 不代替 daemon 讀 Node filesystem、每次檔案操作重新 canonicalize、**PostgreSQL/log/audit/metrics 一律不存 terminal bytes 或 file content**、daemon 不以 root 長期執行）。相關技能：`fastapi`、`go-daemon-development`、`vue-naive-ui-workflow`、`cliora-security-review`、`timezone-precision`、`webapp-testing`、`terminal-websocket-protocol`。
4. 需求變更先更新 `research/prd.md`／`tech.md`／`style.md`，再同步 `research/01/06-requirement-traceability.md`，不得在 implementation ticket 中暗自擴張範圍。**P4 特別容易發生的範圍擴張**：把 metrics export 做成完整監控平台、把 audit 做成 SIEM、把 update 做成自動排程升級、把 Dashboard 做成自訂儀表板。這些一律不做（見 `00-execution-plan.md` §8）。
5. 所有時間採 tz-aware；持久化用 timezone-aware PostgreSQL 型別，傳輸 RFC 3339 UTC（`Z`），畫面才本地化；heartbeat 逾時、update health check、graceful shutdown drain、alert 判定與 relay timeout 全部以 **monotonic** 計算。Dashboard 的「最後更新時間」必須是資料本身的 aware timestamp，不是畫面渲染時間。
6. **Metrics、audit 與 log 是三個不同的 sink，界線不得模糊**：metrics 只放低基數聚合值（op/code/reason/runtime/status，**不得有 path、keyword、檔名、user id、node id 作為 label**）；audit 放可追蹤的營運事件（actor/resource/request_id + 最小化 metadata）；log 放除錯脈絡（結構化 + redaction）。三者都不得出現 secret、token、terminal bytes 或 file content。

## 完成結果

P4 通過時：Admin／Developer／Viewer 的權限在 HTTP、browser WS、daemon WS 與 UI 四處由同一份 domain policy 決定，且 attach/takeover/terminate/read file 都有明確的資源範圍與 owner 規則，Viewer 的任何偽造 mutation 一律以 403/丟棄失敗並留下記錄。SEC-006 清單的每個重要操作都產生**單一可追蹤**的 audit（含 actor、resource、`request_id`、aware timestamp），Admin 可在 UI 以條件過濾與分頁查閱且看到本地時區，redaction 測試證明其中沒有 terminal bytes、file content、password 或 token。Dashboard 顯示真實聚合（online/offline nodes、running sessions per runtime、runtime health、recent activity、異常 Node），部分後端失敗時以 partial + freshness 標示而**不偽裝即時資料**，所有原型硬編碼值、CDN 字型、`min-width` 與孤兒元件已退場。Backend 與 daemon 指標涵蓋 tech §18.1/18.2 清單並可被 scrape，heartbeat 資源有持久化與趨勢，heartbeat loss／queue saturation／timeout surge／DB exhaustion／update failure 有可在演練環境觸發的告警與 runbook。代表性負載（100 nodes、10 sessions/node、500 terminal WS）下記憶體有界、slow client 與 flood 不造成 unbounded 成長。`agentd update` 只接受 allowlisted release、強制驗 checksum、原子替換後跑 health check、失敗自動 rollback、期間 tmux session 保留且重啟後 reconcile，全程 non-root 且有 audit。PostgreSQL 備份／還原已演練且證明不含 terminal raw log，正式部署有 HTTPS/WSS、secret 注入、正確 migration 順序、readiness 與 graceful shutdown。最後：PRD 第 19 節 20 項 MVP 驗收條件全部有測試或操作證據、tech §23 安全基準 15 項全數簽核且無未處理 Critical/High finding、NFR latency/scale/availability 有量測結果（未達標項有明確 release decision）、發布版本可重建／可部署／可 rollback／可觀測並有 runbook。
