## 規劃階段已盤點的既有缺口（P4 要修的，不是新功能）

這些是讀 repo 現況時發現的**真實缺口**，不是規劃上的新增範圍。列在這裡以免實作時被當成 nice-to-have 而跳過。

1. **越權：授權只看 role，沒有資源範圍**。`session.terminate`／`terminal.takeover` 只檢查 role，`TerminalSession.user_id` 存在卻未被用於授權 → **任何 Developer 可終止或搶走他人的 session**。research §P4-W1 明確要求 owner 規則。修在 P4-03。
2. ~~**`audit.view` 是死權限**~~。**已於 P4-05 關閉**：`GET /api/audit` 落地、`UNENFORCED_ACTIONS` 清空。原始問題為 `0002_seed_roles` 已給 Admin、`rbac.py` 已定義，但全 repo 無任何 endpoint 使用。
3. **audit 沒有 `request_id`**。`request_id_var` 只進 log 不進 audit，因此 audit 無法與當時的 log 串接。research §P4-W2 要求「actor/resource/request ID」。修在 P4-04。
4. **`audit_logs.user_id` 無索引**。依 actor 過濾會全表掃描；也缺 `(created_at, action)`／`(created_at, user_id)` 複合索引。修在 P4-04（實作為 migration **`0008`**，因 RBAC 不需 migration 而讓出編號；共 4 個索引）。
5. ~~**production bundle 對外連 CDN**~~。**已於 P4-07 關閉**：`styles.css` 整檔刪除，改用系統字型堆疊，`dist` grep 斷言無 `fonts.googleapis`/`unpkg`/`jsdelivr`/`cdn.`。
6. ~~**`body{min-width:1180px}` 與原型 CSS 仍在全域**~~。**已於 P4-07 關閉，且處置比規劃時假設的更乾淨**：規劃說 `.primary`/`.danger`/`.head`/`.panel` 仍被 9 個檔案使用、所以「是遷移不是刪檔」——那份盤點數的是**使用次數**，不是**未被遮蔽的**使用次數。實際以腳本逐一比對 `styles.css` 的 93 個 class 與每個 `.vue` 自己的 `<style scoped>` 後，**未被遮蔽者為 0**：每個仍在使用的 class 都已在該檔自己的 scoped style 中定義（`.link.danger`、`.tree-panel`、`button.primary` 等），legacy 變數 `--side`/`--top`/`--border`/`--muted`/`--terminal` 的檔外引用也是 0。因此不需要任何遷移，整檔可刪；唯一需要保留的是元素層 base，而那些規則 `tokens.css` 早已有了。

## 實作過程中對計畫的修正（P4-01…P4-15）

計畫是以讀 repo 為基礎寫的，但有幾項只有真正動手才會知道。以下是與 `00-execution-plan.md` 的差異，皆已反映在程式與 ADR 中。

### 1. RBAC **不需要** seed migration `0008`

計畫假設 P4-03 要以 `0008` 對齊角色權限。實際比對後：`0002`+`0006`+`0007` 疊加後的三角色 action 集合**與 `ROLE_ACTIONS` 完全一致**（Admin 10 項、Developer 7 項、Viewer 3 項），P4 也沒有新增任何 action key（audit 用既有 `audit.view`、favorites 用 `session.create`、node update 用 `node.manage`、metrics 用 scrape token 而非 action）。

**缺口從來不是 seeding，而是 enforcement。** 因此 P4-03 不建立空的 migration（那只會製造一個無效果的 revision），改以 `test_role_actions_match_the_seeded_database` 斷言宣告與 DB 一致。`0008` 這個編號**釋出給 P4-04 的 audit 索引**，後續 migration 依序遞補（audit 索引 `0008`、`node_metric_samples` `0009`、`workspace_favorites` `0010`、update 狀態 `0011`；前兩者已落地）。

### 2. `terminal.takeover` 必須同時要求 `terminal.operate`（ADR 0016 已修訂）

ADR 0016 初稿寫 takeover =「owner **或** 持有 `terminal.takeover`」。實作時發現這在**降級**情境下是破口：一個 Developer 建立 session 後被降為 Viewer，他仍然「擁有」那個 session，於是 owner 分支會讓他繼續接管並輸入。已改為 write/takeover 皆先要求 `terminal.operate`，並以 `test_owner_without_operate_cannot_write` 與 `test_demoted_owner_loses_write_and_terminate` 兩側鎖住。

### 3. `test_every_action_is_enforced_somewhere` 一開始是**假通過**

第一版掃描 `backend/app/**/*.py` 找 action 字串，結果 `audit.view` 被判定為「已enforce」——因為 `0002_seed_roles.py` 這個 **seed migration 本身**含有該字串。這使檢查完全失效，也正是 `audit.view` 從 P1 起死了三期卻看起來存在的原因。修法：掃描排除 `migrations/`（宣告 ≠ 執行）。修正後 `audit.view` 正確被判定為未 enforce，因此明列於 `UNENFORCED_ACTIONS`，並在 `rbac.py` 註明 **P4-05 落地 `GET /api/audit` 時必須移除**；該測試雙向失敗（漏列與殘留都會紅），所以這個提醒不會被忽略。

### 4. 兩個 create-path 缺陷（P4-03 自己引入，當場修掉）

- `SessionDetail.from_model` 的 `viewer` 原本有 `None` 預設值，`create_session` 忘記傳 → **剛建立 session 的人被告知自己什麼都不能做**。改為必填（keyword-only 無預設），讓遺漏變成型別錯誤，並加 `test_created_session_reports_its_creators_capabilities` 回歸（因為「型別正確但語意錯」的預設值騙得過 mypy）。
- 矩陣測試第一版讓 session 由 **Admin** 持有，於是 Developer 對 `DELETE /api/sessions/{id}` 得到 403 而測試判定為「持有 action 卻被拒」。這是把 action 層與 owner 層混在一起測。改為 session 由**受測角色本人**持有，owner 規則由獨立測試覆蓋——否則一個漏掉的 action 檢查可以躲在通過的 owner 檢查後面。

### 5. P4-04：redaction 一開始**過度**遮蔽，把要記的事實蓋掉了

key 子字串比對刻意寬鬆，於是 `credentials_revoked: True` 命中 `credential` 而被寫成 `***`——一筆本來要說明「憑證已撤銷」的 audit 變成什麼都沒說。修法：**布林／數值／None 不遮蔽**（它們本身不可能是機密），字串、bytes 與容器照舊遮蔽。同一原則已存在於截斷路徑（保留計數以便閱讀），現在兩處一致。7 個參數化案例鎖住。

### 6. P4-04：`authz.denied` 需要 pure ASGI middleware，`BaseHTTPMiddleware` 不行

`BaseHTTPMiddleware` 會在獨立 anyio task 中執行下游 app，因此 route 內 `denial_var.set()` 寫在**子 context**，middleware 之後讀不到。改為直接呼叫 `self.app(scope, receive, send)` 的 pure ASGI middleware 後才在同一 context。另外 middleware 順序必須讓它**位於 `RequestIdMiddleware` 內側**（`add_middleware` 後加者在外），否則寫 audit 時 `request_id_var` 已被 reset，該筆 audit 就無法與請求 log 對接——這正是加 `request_id` 的目的。

### 7. P4-04：失敗登入的 audit 會被 rollback

`AuthService.login()` 寫了 `user.login_failed` 後就 raise，route 從未 commit → audit 被回滾。沿用 codebase 既有慣例（`sessions.py` 對 FAILED session 的處理）：route 在 `except ApiError` 中 commit 再 raise。**「audit 必須比它所記錄的操作活得久」**是這類事件的共同要求。

### 8. P4-04：測試用的 process-wide engine 跨 event loop

middleware 以自己的 session 寫 audit（刻意如此：請求自身的 transaction 可能已 rollback），走的是 process-wide `get_database()`。它 lazily 建立並綁定當時的 event loop，而每個測試有新 loop → 第二個測試起每次寫入都以 `Event loop is closed` 失敗，只是被 `except` 吞成 warning。修法：`api` fixture 在前後各 `reset_database()`。這是**測試基礎設施**的缺陷，不是產品缺陷（production 單一 loop），但它會讓這條 audit 路徑在 CI 中假綠。

### 9. P4-04：一個既有 P1 測試編碼了舊的雙筆行為

`test_remove_severs_connection_and_revokes` 斷言 `node.remove` **與** `credential.revoke` 同時存在。改為單筆 + metadata 斷言，並在測試中註明變更理由——這正是 ADR 0016「這是行為變更，不只是新增」所預期要處理的。

### 10. 路由與前端常數的實際不一致（計畫未預見）

- enrollment 路由前綴實際是 `/api/enrollment-tokens`（計畫文件寫 `/api/enrollment`）。已於 `ROUTE_ACTIONS` 更正，並由 `test_every_mounted_route_is_in_the_matrix` 保證不再偏離。
- `dto.ts` **缺 `ACTION_AUDIT_VIEW`**，因此前後端 action 集合不一致。已補；`test_all_actions_match_the_frontend_constants` 從第二個角度再次證實了 `audit.view` 的死權限狀態。

### 16. P4-11：容量 harness 自己錯了四次，而每個錯誤版本都**通過**

這是本期最值得記下來的一件事。harness 是用來證明有界性的，但它的前四個版本各自以不同方式量錯，且都顯示綠燈：

- **「不呼叫 `recv()`」不是 slow client。** `websockets` 函式庫有背景 task 把 socket 讀進自己的佇列，所以 Central 看到的是一個健康的讀者，queue 上限永遠碰不到。真正的 slow client 必須是**手刻的 raw socket 且 `SO_RCVBUF` 調小**——loopback 的 kernel buffer 會自動長到數 MB，光是不讀還不夠。
- **drain 讀到的是 backlog + 同時仍在流入的輸出**，總量因此超過 queue 上限，而超出的原因**不是**上限被違反。必須在 drain 前先停掉該 session 的輸出。
- **只有 writer 的輸入會被轉發**（SEC-002），所以當 slow/flood client 先連上時，該 session 完全沒有 timed echo，8 個 normal client 有 4 個量到 0 筆——讀起來**完全像是「relay 在負載下劣化」**。修法是讓 normal client 先訂閱每個 session。
- **filler 輸出未加 tag**，隨機 bytes 偶爾會 unpack 成看似合理的 timestamp，把捏造的樣本灌進延遲分佈。

教訓：**量測工具的綠燈需要和產品的綠燈一樣被懷疑**。每一項都是「先看到一個說得通的數字，再去問這個數字是怎麼來的」才發現的。

### 17. 逐項簽核找到的兩個真實缺陷（P4-11／P4-14）

- **tech §23 #14 的 per-user session 上限不存在**。只有 `sessions_per_node_max`，因此一個帳號可以持有 `nodes × (per_node − 1)` 個 session——100 台就是 900 個——而不觸發任何上限。**會隨 fleet 成長的上限不是上限**。已加 `sessions_per_user_max`（預設 20）。它能撐到 P4 的原因很單純：**既有測試全都只用一個 node**，而 per-node 檢查在單 node 情境下表現完美；新測試因此刻意跨**兩個** node 斷言。
- **terminal queue overflow 後連線沒有被關閉**。`pump()` 送出 `terminal.gap` 就 `return`，socket 留著、pump 已死：browser 收到 gap 之後再也收不到任何 byte，卻仍計入 `active_terminal_connections`、仍訂閱著 relay，**而且如果它是 writer，就一直佔著它已經無法使用的 writer 標記**，別人無法用正常途徑接手。已改為關閉 1013。它能撐到 P4 的原因：**每個既有測試都斷言 gap「被送出」，沒有一個斷言「然後呢」**。

### 18. 兩個只在「別人來跑」時才會出現的腳本缺陷

- **`queue-saturation.sh` 呼叫 load harness 用的是一個從不存在的 CLI**。該 drill 寫於 P4-09，當時 harness 還沒有；P4-11 交付時介面不同，而沒有任何東西發現。**跑不起來的 drill 與燒不起來的告警無法區分**，因此新增 `test_drill_harness_flags_exist` 比對兩者（並以注入假 flag 反向驗證過它不是空測試）。
- **相對路徑的 `$OUT` 搭配子 shell 裡的 `cd backend`**：重導向會相對 `backend/` 解析，於是 log 寫入失敗、整個子 shell 在啟動任何東西之前就死了，症狀是「Central 沒有 ready」而且沒有 log 可看。手動跑時傳的是絕對路徑所以永遠看不到；CI 傳的是相對路徑。兩支腳本現在都在最前面把 `$OUT` 轉成絕對路徑。

### 19. 把 nginx 真的跑起來，找到三個缺陷，並推翻了缺口自己的前提

`docs/p4-report.md` §4.1 原本誠實地記著「nginx 只被審閱、未被執行」。**寫下來並沒有關掉它。** `scripts/p4/verify-edge.sh` 以真實 nginx image + 出貨用的設定檔 + 自簽憑證 + 真實 console build，對一個 throwaway Central 做 **25 項 over-the-wire 斷言**，於是三個缺陷從「讀起來正確」變成「斷言失敗」：

1. **HTML 頁面與 JS bundle 上的安全標頭全部不存在。** nginx 的 `add_header` **不會**繼承進一個自己宣告了 `add_header` 的 location，而 `location /` 與 `location /assets/` 都設了 `Cache-Control`——於是 HSTS／CSP／`X-Frame-Options` 正好在最需要它們的那些回應上被靜默丟棄，而 server 層的那一段讀起來像是生效的。現在每個 location 各自重複一份，並且兩處都被斷言。
2. **CSP 是一個不合法的 HTTP/2 標頭。** 它原本以行尾反斜線分成多行；**nginx 的引號字串沒有行接續**，所以反斜線與換行進了標頭的**值**。curl 直接以 error 92 拒收整個回應，瀏覽器也一樣——頁面壞掉**而且**政策沒有生效。現已改為單行。
3. **`/api/metrics` 可以從外部打到。** `location /api/` 是前綴比對，因此它把 `/api/metrics` 一起代理出去，而正上方兩行的註解寫著它「deliberately not exposed here」。**註解不是規則**，exact-match 的 `return 404` 才是。

**而且這個檢查本身一開始是空的。** 它聲稱驗證「閒置 WebSocket 能穿過 proxy 存活」，但 uvicorn 預設每 **20 秒**送一次 ping，每次都會重置 `proxy_read_timeout`——所以把 timeout 設成 20s 它**依然通過**（實際設下去驗證過）。現在 Central 以 `--ws-ping-interval 600` 執行讓連線真正閒置，並做過反向驗證：對 20s timeout 於恰好 20.0s 失敗、對出貨的 3600s 於 70s 通過。

**真正的不變式是 `proxy_read_timeout > ws_ping_interval`**，不是「大於人類停頓時間」——後者是設定檔原本自己寫的理由，而它是錯的。這一項同時說明了為什麼「把缺口寫下來」和「把缺口關掉」是兩件事：前者讓一個錯誤的風險敘述被保存了下來。

- 2026-07-25（P4-06）：Dashboard aggregates 與 freshness 契約。**六個 block 各有獨立取數函式與獨立狀態**：任一失敗只讓該 block 變 `degraded`（`data: null` + `error_code`），回應仍是 200 且其餘五個顯示真實數字——整體 try/except 會把一個壞查詢變成空白頁，而「吞掉錯誤回 0」更糟（會把故障報成健康的空 fleet）。freshness 的三個 stale 觸發條件都有各自理由：**(1)** Central 啟動未滿一個 heartbeat interval（此時「全部離線」與「還沒收到任何人的消息」是同一個觀測，把前者當事實發佈正是本契約要防的事，故新增 `clock.process_uptime_seconds`）；**(2)** 有連線但心跳靜默超過 30 s（socket 還開著所以仍計入，但它貢獻的數字已超過可當作「當前」的期限）；**(3)** 儲存的 `nodes.status` 聲稱的存活度高於 registry 能背書的程度——**只檢查這一個方向**，因為 `nodes.status` 自 P1 建立後從未被更新（永遠是 `offline`），若雙向都算不一致會讓 block 永久 stale。節點狀態一律經 `compute_status()` 重算，不讀 `nodes.status`。**快取放的是全保真資料，role projection 在快取之後**：先redact再快取會讓「第一個發問的角色」決定後續每個角色看到什麼（已由 `test_a_cached_summary_is_projected_per_viewer_not_shared_verbatim` 鎖住）。無樣本時 `resources` 回 empty 而**不是 0**（0% CPU 與「沒有資料」是不同事實）；runtime 的 `unknown` 是獨立結果而不併入 `unavailable`（沉默不等於否定，否則全新 fleet 看起來全壞）；`unhealthy_nodes` 截斷到 10 筆但**回報未截斷前的 total**（否則清單會暗示自己是完整的）。`node_metric_samples` 每欄位皆 nullable（daemon best-effort 取樣，讀不到必須存 NULL——存 0 會讓「讀不到磁碟」看起來像「磁碟是空的」，且任何 fleet 平均都會靜默失真），fleet 平均**先每 node 取最新樣本再跨 node 平均**（否則一個高頻上報的 node 會壓過安靜的 node）。降頻寫入用 registry 的 monotonic per-connection 時間（不查 DB），且**在嘗試前就佔用時槽**——這同時對「持續失敗」限流；寫入包在 savepoint 內，失敗只計 `metric_persist_error_total` 並保持 transaction 可用，因此決定存活性的 `last_seen_at` 不會被歷史列拖垮。
- 2026-07-25（P4-10）：daemon release 與安全更新。**整個設計的安全性寫在型別簽章裡**：`Updater.Update(ctx, version string, allowDowngrade, dryRun bool)` ——沒有 URL、檔名、digest 或路徑參數，CLI 也沒有 `--url`/`--file`/`--checksum`，全部由 manifest + 本機 config 推導；`TestUpdateAcceptsNoArtifactReference` 以 reflection 鎖住這個簽章，因為「先加個 --url 方便測試」正是會重新打開 protocol 已關閉破口的那種改動。manifest **fail closed**：檔名通過封閉 allowlist、檔案存在、`checksums.txt` 有對應 digest、size 相符，四者缺一即不列出（列出但無法驗證的項目會讓失敗從「不提供」變成「下載完才在 node 上炸掉」）；allowlist regex **與 `downloads.py` 共用同一個常數**（兩份副本終將分歧，而分歧的方向決定「node 更新不了」或「advertise 了不能用的東西」）。六個 stage 的順序本身是設計：**verify-then-swap**——digest 相符後還要在暫存位置**執行** `agentd version` 確認它自稱的版本，兩者都過才動已安裝的 binary，因此壞 artifact 一律在安裝物未被觸碰時失敗。備份是 **copy 而非 rename**（rename 會留下「路徑不存在」的空窗，`systemctl restart` 落在其中就會失敗且無物可回復）。rollback 邊界僅 binary + unit（不回復 config/credentials，新版可能已合法改寫，回復反而讓舊版讀到不能解析的檔案）；**rollback 自身失敗回 `failed` 而非 `rolled_back`**，因為「已收斂」與「需要人到機器上」是兩件事。提權採 ADR 0017 方案 (a)：`Available()` 在**任何網路/磁碟動作之前**檢查 root，非 root 一律 `UPDATE_NOT_ALLOWED`；這同時避開一個陷阱——執行 `systemctl restart agentd` 的程序**不能是**被重啟的那個 unit，否則它在 health check 與 rollback 之前就死了。Central 端：**relay timeout 不等於失敗**（重啟會切斷回覆要走的 socket，標成失敗會回報一個從未發生的 rollback，而且最常發生在真正成功的情況），因此逾時保持 `in_progress`，由 daemon 重啟後主動上報的 `daemon.update_result` 或下次註冊收斂。
- **本機實測發現並修掉的一個真實缺陷**：`--dry-run` 原本仍會先過提權閘門，而 staging root 固定在 `/var/lib/agentd/update`（需 root 建立），因此**非 root 的預演根本跑不起來**——正是 `--dry-run` 存在的目的。改為 dry run 不受提權閘門阻擋（但在結果訊息中明說缺提權），且 staging root 不可寫時退回 `os.MkdirTemp` 的 0700 私有目錄（真實更新仍**必須**用 doctor 會檢查權限的固定 root，否則暫存 binary 會落在 checksum 與 swap 之間未受檢查的位置）。這個缺陷單元測試看不出來，是用真實 binary 對真實 Central 跑出來的。
- **P4-10 本機真實驗證**（非 mock）：以 `-trimpath` 連續建置同一 commit 兩次 → checksum 相同（reproducible，ADR 0017 的驗證方式）；起真實 Central（`artifacts_dir` 指向真實 tarball + `checksums.txt`）後用真實 `agentd` 走完 manifest → 下載 → sha256 → 解壓 → 執行 `agentd version` 驗版本：成功 dry run、**篡改 artifact → `UPDATE_CHECKSUM_MISMATCH`**、未發佈版本 → `UPDATE_NOT_ALLOWED`、非 root 真實更新 → `UPDATE_NOT_ALLOWED`。

- 2026-07-25（P4-09）：observability。**label allowlist 是這張 ticket 的核心決定，且在呼叫點強制而非事後掃描**：metrics 是唯一**沒有 redaction** 的 sink（log 有、audit metadata 有最小化，但 metric label 是原樣發佈給任何能 scrape 的人），因此 user id/path/keyword 進 label 既是高基數也是資訊揭露；`increment`/`observe` 對未知 key **丟例外而不是丟掉那個 label**——後者會讓指標「看起來正常」，錯誤要等到有人看著一條把所有東西聚合在一起的曲線才會發現。HTTP 延遲以 **route template** 而非實際 path 標記（否則每個 session id 都是一條新 series，且永不回收），未匹配的請求收斂為單一 `<unmatched>`（否則掃描器打一千個 URL 就長出一千條 series）。exporter 預設關閉 + **專用 scrape token**（不複用 `audit.view`：那會逼人為了抓數字而建一個能讀稽核軌跡的服務帳號，而 Prometheus 不持有 user session），停用時回 **404 而非 403**（讓探測者無法從回應判斷這個部署有沒有設定 metrics）。**histogram 的 cumulative 轉換**在出口做：registry 為了記錄路徑 O(1) 而只放進一個 bucket，若直接輸出，`histogram_quantile` 算出來的不是不精確而是**錯的，且錯得很像對的**。gauge 於 scrape 時即時取數（存起來的 gauge 只會是舊的），**單一 gauge 逾時或拋錯只略過該指標**並計入 `scrape_error_total`——在某件事已經很慢的時候失去全部可見度，比失去一個數字糟得多。daemon 端**刻意不開 Prometheus 埠**（trust boundary 是 outbound-only，在每個 node 上開監聽埠會一次性反轉整個 fleet 的邊界），改以既有 heartbeat 傳遞 + `agentd metrics` 印到 stdout；此決定由 `TestThisPackageCannotOpenAPort` 以「該套件不得 import net/net/http」的結構性斷言守住（行為式的「連不上」測試會因為錯的理由通過）。alert 規則 12 條，每條都必須指名一份存在的 runbook、只引用真的會被匯出的指標，並有一支可觸發它的 drill 腳本——這三件事都是測試而不是慣例，因為「沒人見過它 fire 的告警」等於沒人知道怎麼處理。
- **P4-09 期間抓到的一個真實排序缺陷**：exporter 原本先 `export_series()` 再算 gauge，於是 gauge 逾時所記的 `scrape_error_total` **不會出現在報告它的那次 scrape 裡**，要到下一次才看得到。這會讓該計數器永久落後一個 scrape 間隔，是任何在它上面寫告警的人都會踩到的陷阱。改為先算 gauge 再快照。
- 2026-07-25（P4-08）：Dashboard UI。整個頁面圍繞**三項拒絕**建構：**(1) 預設不自動輪詢**——會自己刷新的頁面看起來是即時的，即使底下的 block 是 `stale`，那正是 freshness 契約要防的錯覺；30 s 自動更新是 opt-in 的開關，狀態放在 store 所以切頁後保留（那是使用者偏好，不是請求狀態）。**(2) 有資料後不再顯示 skeleton**——skeleton 的意思是「第一次取數中」，每 30 s 出現一次會製造虛假的活動感；refresh 期間保留數字，只在角落顯示 refreshing。**(3) 一個 block 壞掉只降級一張卡**——退化卡**完全不顯示數字**（為讀不到的值顯示 0 是編造），並列出 `error_code` 與重試；頁面頂端另有一次「有 N 個區塊無法取得」的整體提示。`stale` 的處理是**仍然顯示數字**並以文字說明「可能不是最新狀態」——藏起來是另一種謊，資料是真的，只是比契約允許當作「當前」的期限更舊；stale/degraded 皆以**字＋符號**標示而非僅靠顏色（WCAG 1.4.1）。fleet 資源在無樣本時顯示 `—` 與「尚無資料」而**不是 0%**，同時保留「真正的 0 仍顯示 0」的反向測試。相對時間來自 server 的 `generated_at`（取數時間），因此快取命中時顯示「10 秒前」而不是「剛剛」——那是契約在運作。異常 Node 每列說明**原因**（只有名字對維運者毫無新資訊），截斷時明說「共 N 筆」。非 Admin 的最近活動以一行說明「只有 Admin 能看到執行者」，而不是留下一排無解釋的破折號（那會被讀成「這些事件沒有執行者」）。
- **P4-08 期間以真實後端載入頁面時發現的一個 server 端缺陷**：剛啟動的 Central 即使**節點數為 0** 也把 nodes block 標為 `stale`（uptime < heartbeat interval 的規則）。但 total==0 是因為表是空的，等待心跳不會改變它——這會在「新安裝者正在判斷產品能不能用」的那一頁，於一個確定的數字旁邊寫上「可能過時」。已修為空 fleet 豁免該規則，並補兩個測試（含「有節點時仍必須 stale」的反向鎖）。這是 fixture 測不出來的，只有對真實 server 打一次才會看到。

- **本機驗證注意**：沿用 P3 的教訓——E2E 使用獨立資料庫並在結束後 drop，避免污染有首筆計數斷言的 `cliora_test`。install-update matrix、真實 systemd restart、WebKit、真實 TLS 與 100-node 規模在本沙箱無法執行（見 [[installer-sandbox-limits]]），必須由 CI 覆蓋且在證據包中與本機結果分開記錄。
- 2026-07-25（P4-13）：workspace 收藏與最近使用。核心前提是**收藏是 UX 捷徑、永遠不是授權來源**，因此 `services/favorites.py` **匯入** `sessions.authorize_workspace` 而非複製 prefix 規則——第二份實作終將分歧，而分歧的方向會決定一個被儲存的路徑能否逃出它的 root。可用性判定（`usable`／`node_offline`／`node_disabled`／`outside_allowed_root`）**每次讀取都重算、絕不儲存**：收藏當下合法的 root 之後可能被移除。刪除他人的收藏回 **404 而非 403**（403 會確認該 id 存在，讓 per-user 清單變成探測他人資料列的工具），且與不存在的 id 回**完全相同的 error body**。`recent` 由 `terminal_sessions` 推導、無新表，且**已終止的 session 仍計入**（「最近用過」是歷史，回到做完事的地方正是這個功能的用途）。`..` 以 **segment** 判定，因此 `..config` 這個合法目錄名不會被誤擋。**本機實測發現的一個缺陷**：POST 回應原本硬寫 `usability: "usable"`，但 `add()` 刻意允許收藏一個離線 node 上的路徑，於是 POST 回 `usable` 而緊接著的 GET 對同一列回 `node_offline`——UI 的樂觀星號會無故翻面。改為兩者走同一條判定路徑，並補上會抓到它的測試。
- 2026-07-25（P4-11）：容量與有界性 harness。設計原則是**斷言而非印數字**：每個 scenario 回傳帶 pass/fail 的 `Check`，orchestrator 有任何一項失敗就非零退出——只印數字的 harness 一個 release 內就會變成裝飾。延遲量的是**完整往返**（輸入自帶 `perf_counter` 戳記，假 daemon 原樣回送），只量單程會回報約一半的數字並通過產品其實沒達到的預算。harness 自己錯了四次而每次都通過（見上節第 16 項）。**找到並修掉 overflow 後連線未關閉的真實缺陷**（第 17 項）。
- 2026-07-25（P4-12）：部署資產與 graceful shutdown。migration 為獨立 one-shot job 而**不在 lifespan**——多副本會互相競態，重啟會變成非預期的 schema 變更；順序錯誤由 `/readyz` 比對 migration head 抓到，因此是被**偵測**而非只是被文件叮嚀。drain 的順序有意義：先告訴每個 browser **為什麼**要斷線（`session_preserved: true`），再關 daemon socket（daemon 走既有 backoff）；**任何情況都不終止 CLI session**——NFR-002 說瀏覽器斷線不得終止 session，Central 重啟是同一個承諾的另一面，也是最容易被「順手清理」的 shutdown hook 打破的那一個。nginx 有兩個易錯且昂貴的設定：`/ws` 的 `proxy_read_timeout`（預設 60 s 會每分鐘殺掉閒置終端）與 CSP 的 `worker-src blob:`（缺了 Monaco 會空白）。
- 2026-07-25（P4-14）：安全審查。逐項簽核的價值在這期得到證明——**第 14 項的 per-user 上限根本不存在、第 15 項只做了一半**（見第 17 項），兩者都不是讀程式碼看得出來的。文件的規則是「每一列都要指到可定位的測試名稱」，而寫的過程中確實抓到三處引用錯誤（`token_version` 不在我以為的檔案、ws-ticket 單次使用在 `test_security.py` 而非 sessions 測試），以腳本掃過全文的路徑與測試名稱才發現。
- 2026-07-25（P4-15）：驗證與 MVP exit。`p4.yml` 11 個 job **無任何 `continue-on-error`**——能在檢查失敗時仍為綠的 gate 不是 gate；`evidence` job `needs` 其餘全部，因此紅色 run 產不出證據包。`evidence.sh` 對不可執行的 leg 一律**列入 `skipped.txt` 而非靜默省略**（悄悄少跑一個 gate 的證據包讀起來就是通過，這是證據包唯一不能有的失敗模式）。同理，drills 有三態而非兩態。修掉兩個只在「別人來跑」時才出現的腳本缺陷（第 18 項）。**尚未在真實 runner 執行過**，這是 `docs/p4-report.md` §5 的 Go 條件第 1 項。
