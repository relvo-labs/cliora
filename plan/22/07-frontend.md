# 07 — 前端（`RQ-10`）

**本期最大的一塊，而它的起點比預期高也比預期低。**

高：Requirements 分頁已經在（`ProjectDetailView.vue:427`）、
需求詳情頁已經在（`RequirementDetailView.vue`，361 行）、
版本比較的骨架已經在（`comparedSpecs`，`:125`）、
`blocking_questions` 已經從 API 送過來（`requirements.py:155`）。

低：**現有的介面是三個 JSON 文字框。**
`criteriaJson`、`questionsJson`、`proposalJson`（`:28-30`）——
V2.1 交付的是「資料模型與人工流程」，而人工流程目前的形狀是「請貼一段 JSON」。

> **所以本期前端的工作不是「加一個頁面」，是「把三個 JSON 文字框換成三個可以做決定的介面」。**

## 1. Requirements 分頁：從清單到入口

### 1.1 Intake 輸入框

**一個 textarea 加一顆按鈕，沒有第二個欄位。**
`requirements.create` 只吃 `raw_text`（`requirements.py:145-151`），
而那個設計的理由（「十個必填欄位是流程停止被使用的方式」）在前端要看得出來：
不要在旁邊放「優先度」「預估工時」的下拉。

輸入框上方一句 placeholder 級的引導：
**「用你自己的話寫，不通順也沒關係——後面會有人（或 Agent）問你問題。」**

### 1.2 兩顆派工按鈕，以及它們什麼時候可按

| 按鈕 | 可按的條件 | 按下去做什麼 |
|---|---|---|
| **派給 Agent 釐清** | `status ∈ {intake, clarifying}` ＋ 有 `run.dispatch` | 建立一張 `card_kind: clarification` 的卡並 dispatch（§1.3） |
| **派給 Agent 拆解** | `status = 'approved'` ＋ 有 `run.dispatch` | 建立一張 `card_kind: decomposition` 的卡並 dispatch |

**不可按時要顯示原因，不要只是灰掉。**
拆解按鈕在需求未核准時的 tooltip 是
「先核准規格。未核准的規格不能被拆解——這是 API 層的規則，不是介面的限制。」

### 1.3 「建立卡片並 dispatch」是兩個請求，而中間會失敗

按鈕做的事是 `POST /tasks` 然後 `POST /tasks/{id}/dispatch`。
**第二個會失敗**（`03-…md` §1.2 的四道拒絕都在 dispatch）。

失敗時**卡片已經建好了**。三個處置：

1. 錯誤訊息要說「卡片 TASK-42 已建立，但派工被拒：<原因>」，並附卡片連結。
2. **不要自動刪掉那張卡。** 一個會在失敗時刪東西的按鈕，
   在部分失敗時會刪掉不該刪的（例如 dispatch 因為「沒有可用的 runner」而失敗——
   那張卡完全正確，等一下再派就好）。
3. 需求詳情頁要顯示「這個需求已經有一張釐清卡（TASK-42，未派工）」，
   避免第二次按建立出第二張。

## 2. 卡片訊息串：重用，不新做

`research/02/07` RQ-08 明寫「**重用 V2.2 的卡片訊息串元件**，不新做。差別只在頁面位置」。

**本期的落實方式是：需求詳情頁不放訊息串。**

看起來反直覺，理由是 D28 §1 的「不新增管道」：
如果需求頁上有一個訊息串、卡片頁上也有一個，
即使它們渲染同一份資料，**使用者仍然會問「我該在哪裡回」**。

所以：需求詳情頁顯示一個**指路區塊**——

```text
釐清中：TASK-42 · 等待你的回覆（3 分鐘前提問）
「報表匯出是指 CSV 還是 PDF？」                    [ 到卡片回覆 → ]
```

引文是最新一則未答的問題，按鈕跳到卡片。
**對話只有一個家**，而需求頁負責讓人找到它。

## 3. 規格審閱：九節 ＋ 未解決問題置頂

### 3.1 版面順序

```text
┌ 未解決的問題（N）              ← 置頂，未解決時是紅色區塊
├ 目標 / 範圍 / 非目標
├ 驗收標準（逐條）
├ ── 以下是 sections 的九節 ──
├ 問題 / 使用者
├ 使用者故事（逐條，可展開看驗收標準）  ← §3.3
├ 使用者旅程 / 功能需求
├ 畫面（表格：畫面 × 狀態）
├ 資料與 API / 安全性與隱私 / 驗證計畫
└ 核准區
```

**未解決問題置頂**是 `research/02/07` RQ-08 的原文要求。
空的時候整個區塊消失（不要顯示一個綠色的「沒有未解決問題」——
那會佔掉最貴的螢幕位置去說一件沒發生的事）。

### 3.2 核准按鈕的三種狀態

| 狀態 | 外觀 | 說明文字 |
|---|---|---|
| 有未解決問題 | 停用 | **逐條列出**是哪幾個問題（`blocking_questions` 已經送過來了） |
| 沒有規格版本 | 停用 | 「先寫一份規格，或派給 Agent 釐清」 |
| 可核准 | 可按 | 「核准之後這個需求就不能再新增規格版本了」——這是 `add_spec` 的既有行為（`requirements.py:191`），**按下去之前要知道** |

**停用的按鈕旁邊一定要有 API 會拒絕的同一句話。**
理由在 `requirements.py:231` 的 docstring：拒絕在 API 層，
「a UI-only rule would not be there when it did」——
而反過來說，**UI 若不說出同一件事，人會以為那是介面的限制而去找繞法**。

### 3.3 使用者故事那一節要能逐條看

`sections.user_stories` 是拆解的輸入（`02-…md` §1.3），
所以它在審閱畫面上的地位比其他八節高：

- 逐條顯示 `title` ＋ `narrative` ＋ `acceptance`。
- 每條旁邊顯示**「拆解後對應 N 張 Task」**（有提案之後才有值）。
- **不提供勾選。** Monstrare 的 `project-kickoff` 步驟 4 是人工勾選 User Story，
  但平台的關卡是**規格核准**（整份）與**提案接受**（逐張 Task）。
  在中間再插一層勾選會變成第四個關卡，而 D28 只有三個。

### 3.4 版本比較：並排，不做字元 diff

`comparedSpecs`（`:125`）已經取最後兩版。本期把它變成真的並排：
左邊第 N-1 版、右邊第 N 版，**逐節對齊**，有差異的節加一個左邊框。

**不做字元級 diff**（`00-…md` §4）。
「哪一節變了」是審閱者要的資訊；「這一句的第三個字變了」不是。

版本選擇器：兩個下拉，預設最後兩版，可任選兩版比較。

## 4. 提案樹的接受介面

**本期最重的一個元件，也是三個 JSON 文字框裡最該消失的那一個。**

### 4.1 三層樹狀勾選

```text
☑ Epic: 報表匯出
  ☑ US: 使用者可以選擇匯出格式
    ☑ TASK  後端：匯出格式參數                  PR   medium  DoR 7/7
    ☑ TASK  前端：格式選擇器                    PR   low     DoR 7/7
    ☐ TASK  串接：端到端匯出測試                PR   low     DoR 5/7 ⚠ 缺 2 項
  ☐ US: 匯出進度提示
    ☐ TASK  ...
```

四條規則：

1. **三層可獨立勾。** 勾 Epic 不強制勾底下全部；取消 Epic 不清掉已勾的 Task。
   （`accept()` 只讀 `tree["tasks"]`，Epic 與 US 的勾選目前**不產生任何東西**——
   §4.5 說明這件事怎麼呈現才不會騙人。）
2. **每張 Task 顯示 DoR 的分數與缺項。** `7/7` 是綠、少於就是黃 ＋ 一個可展開的缺項清單。
3. **缺項的卡仍然可以勾。** 它會落 `backlog`，而那是設計不是錯誤——
   勾選框旁的文字要說「會建立在『待辦』，不是『就緒』」。
4. **已接受過的節點顯示為已建立**（帶卡片連結），不可再勾。
   資料來自 `TaskProposalDTO.accepted_item_ids`（`04-…md` §4.3）。

### 4.2 就地編輯

點一張 Task 展開一個小表單，可改的欄位是
`delivery`／`risk`／`target_branch`／`required_labels`／`stage`（`04-…md` §5）。

**`readiness` 不可改**，且要說出為什麼：
「DoR 由拆解填寫。要補齊請先建立卡片，再在卡片上修改——那一步會留下紀錄。」

改過的欄位在樹上顯示一個「已修改」的小標記，
底部的摘要區列出「你改了 2 張卡的 3 個欄位」。

### 4.3 底部摘要：兩個數字，不是一個

```text
將建立 12 張卡片
其中 7 張會開合併請求（pull_request）        ← 獨立一行
3 張會落在「待辦」（DoR 缺項）
2 張的相依指向沒被勾選的卡片，會落「待辦」    ← 04-…md §4.4
                                    [ 接受並建立 ]
```

**第二行是獨立的，理由在 `README` §5.1**：
拆解會把「一個決定，六個 PR」這件事的曝光面乘上一個數量級，
而 V2.4 §6.3 的範圍問題還沒有裁決。**在那之前，讓數字看得見。**

### 4.4 拒絕：理由必填

一個 modal，一個 textarea，**送出按鈕在 textarea 空的時候停用**，
說明文字：「下次拆解時這段理由會進 Agent 的情境包，避免它再提一次。」

——這句話是真的（`04-…md` §4.2），而它同時是最好的填寫動機。

### 4.5 Epic 與 User Story 的勾選目前不產生東西，這件事要誠實

`accept()` 建立卡片時 `epic_id` 與 `user_story_id` 一律是 `None`
（`requirements.py:382-383`）。

**所以樹上勾 Epic 是一個沒有後果的動作。** 三個選項：

| 選項 | 評估 |
|---|---|
| 本期實作「接受時一併建立 Epic 與 User Story 列」 | 範圍會長出來：`epics`／`user_stories` 的 `card_ref` 配號、去重（同名 Epic 已存在怎麼辦）、藍圖分頁的顯示 |
| 樹上不顯示 Epic／US 層 | 樹會變成 22 張平坦的卡，**而分組正是它可讀的原因** |
| **顯示但不可勾，只當分組標題**（採用） | 誠實、零新後果、樹仍然可讀 |

採用第三個，並在 Epic 那一行右側加一句小字：
**「Epic 與 User Story 目前只用於分組，不會建立成獨立項目。」**

**這是一個要記進 `10-…md` §4 的追蹤項**，不是一個永久設計。

## 7. PRD Patch 提案的畫面

Project 的 **Settings 分頁**下一個新區塊，不是新分頁。
理由：它是低頻的東西（一個專案一個月可能零份），
給它一個分頁會讓五個分頁變六個而其中一個永遠是空的。

- 清單只顯示 `pending` 的（部分索引就是為它建的，`02-…md` §3）。
- 點開顯示：`target_path`、四項 `sections`、`reason`、`open_questions`、**diff（唯讀純文字）**。
- 兩顆按鈕：接受（帶「建立套用卡片」的後續按鈕）、拒絕（理由必填）。
- **沒有下載按鈕**（`05-…md` §3.1 第三條）。
