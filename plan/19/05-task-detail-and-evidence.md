## 2. `SourceBadge` 上線：D10 的三處一致

`research/02/09` §7：

> 三種 `source` 徽章（實心／線框／灰字）在 **Evidence、驗證報告、Run 詳情**
> 三個地方要**完全一致**——它是可信度語言，不是裝飾。

三處落點：

| 畫面 | 用在哪 |
|---|---|
| Task 詳情 · 驗證報告 | 每一項 check 的 exit code 旁 |
| Task 詳情 · 證據 | 每一列證據旁 |
| Run 詳情 | run 摘要裡由 daemon 觀測 vs Agent 自述的欄位 |

**「完全一致」靠的是同一個元件，不是靠三處都照著同一份規格寫。**
`UI-04` 的測試已經斷言 `SourceBadge` 是全 repo 唯一產生 source 徽章的地方
（`03-…md` §2.5），這裡只要引用它。

### 2.1 三級的語意（不是三種顏色）

| source | 變體 | 意思 | 誰產生的 |
|---|---|---|---|
| `machine_verified` | **實心** `--source-machine` | 機器事實 | daemon 在 run 內實際執行得到的 exit code |
| `platform_observed` | **線框** `--source-platform` | 平台紀錄 | Central 自己觀測到的（run 起訖、狀態轉換） |
| `agent_reported` | **灰字** `--source-agent` ＋「Agent 自述」 | Agent 說的 | Agent 在 payload 裡填的 |

**視覺權重差必須明顯**，因為它承載的是「這句話你能信到什麼程度」。
三個都做成一樣的藥丸，這一格就白做了。

### 2.2 矛盾不仲裁

prototype 示範了一個情境：git 說 11 個檔案、Agent 自述 9 個。

**兩者都顯示、都標來源，平台不猜誰對。** UI 上的形式是兩列並存 ＋
一個說明框。這不是缺陷展示，是刻意的——平台一旦開始仲裁，
就得為仲裁錯誤負責，而它沒有那個資訊。

若本期 Evidence 資料尚未有此情境，**保留版面能力即可**（同一個 `kind` 出現兩列不會壞版），
不必造假資料。

## 3. 失敗項預設展開且不可摺疊

`research/02/09` §4.5 與 `version2.md` §14.3：

> 失敗的 check 與 AC **預設展開且不可摺疊隱藏**。

實作上要注意的是「不可摺疊」不只是 `open` 屬性——**不要給它摺疊控制項**。
一個可以被收起來的失敗測試，遲早會被收起來。

- 失敗的 check：紅色說明框，含指令、exit code、失敗摘要；
- 失敗的 AC：一樣；
- **成功的項目可以摺疊**，失敗的不行。

### 4.1 審查關卡：核准者與時間要留著

現況已經做對了（`data-gate-approved` 顯示 `approved_by` ＋ `approved_at`），
**這一格不要在重繪時弄丟**。

`research/02/09` §4.5 與 D10／D28 的理由：
每個 gate 存的是**核准者與時間，不是 boolean**。
「Agent 輸出不等於核准」在資料層的形式，就是這一格永遠有一個人類 `user_id`。

同理 `GATE_DISABLED` 的處理（現況已做對）：**停用的關卡要說明自己為什麼停用**
並給出路（`前往設定`）。D31：一個悄悄不存在的關卡比一個說明自己為什麼不存在的關卡糟。
