# Cliora 工作區檔案邊界：圖片投放與文字判定

本目錄交付兩件在 2026-08-01 由使用者指示的變更，ticket 統一使用 `WF-` 前綴（**W**orkspace **F**iles）：

| # | 使用者的話 | 交付內容 |
|---|---|---|
| ① | 「CLI 要加入可以直接透過網頁把圖片放入的功能」 | 貼上／拖放／挑檔三個入口，圖片落到節點工作區內一個**由 daemon 命名**的目錄，路徑以 writer 身分打進終端機輸入行 |
| ② | 「目前 binary 過於嚴格，很多的純文字檔都被認為是 binary 導致無法預覽」 | 判定改為掃描整個已讀取內容、UTF-8 驗證落在 rune 邊界、ESC 視為文字、比例的單位一致，並用一份分類 corpus 把兩個方向都釘住 |
| ③ | 「已經可以撤銷唯讀工作區了，日後會朝向可編輯，平台可以寫進使用者工作區」 | **撤銷** `NFR-005.AC-142`（產品核心原則裡的唯讀那一條），並以 ADR 0024 的 **W1–W4** 取代：每一條寫入路徑都要經 `workspace.Root`、有配額與保留期、每次寫入留稽核、節點可拒絕並回報 |

第 ③ 項是使用者在計畫初稿之後補的指示，它改變了這一期的**性質**：
原本是「在唯讀邊界上開一個例外」，現在是「撤銷唯讀姿態，並交付它的第一個實例」。
差別不在程式碼（交付範圍一模一樣），在於下一條寫入路徑會拿什麼當先例 ——
例外會被重新辯論一次，姿態會被照著做。**這一期仍然不做編輯**（D21）。

## 這一期真正的形狀

兩件事看起來無關，實際上是同一條邊界的兩個方向 —— **什麼可以跨過工作區的邊界**：

```
                     ┌─────────────────────────────────────────┐
   瀏覽器            │            節點的 workspace              │
     │               │                                         │
     │ ① 位元組 ────►│  .cliora/uploads/<UTC 日期>/<ULID>.png   │  ← 這一期新開的方向
     │               │            ▲                            │
     │ ◄─── 相對路徑 │            │ daemon 命名，wire 上沒有     │
     │               │            │ filename／path／directory    │
     │               │                                         │
     │ ◄── 文字內容 ─│  read.go → Classify(整個緩衝區)          │  ← 這一期修對的方向
     └───────────────┴─────────────────────────────────────────┘
              兩個方向共用 workspace.Root（os.Root, RESOLVE_BENEATH）
```

共用的不只是套件與 `os.Root`，還有**同一條產品規矩**：
1.4.0 的 `daemon.update` 只帶版本號、1.6.0 的 `tunnel.open` 沒有 host 欄位、
1.7.0 的姿態只回報不指定 —— 這一期是**請求端不得命名檔案**。
上一期把這條規矩守在 argv 上（`SCOPE-011` 存活的那半條），這一期把它守在檔名上。

## 四項已量測的事實（不是推論）

實測於 2026-08-01、Go 1.26.5，完整輸出在 `08-measurements.md`：

1. **誤判的成因只有一個，而且已定位。** 本 repo 878 個**完全合法 UTF-8** 的文字檔中，
   20 個無法預覽 —— 佔 >8 KiB 且含多位元組字元檔案的 **8.7%**。
   全部的成因都是 `sample[:8192]` 切在多位元組字元中間，導致 `utf8.Valid` 為 false。
   對純中文文件，這個機率是 **2/3**。**沒有一個誤判來自編碼問題**，這直接決定了
   本期不引入編碼猜測（`00-…md` D15）。
2. **`FR-FILE-004` 在反方向上也不成立。** 前 8 KiB 都是可列印 ASCII 的二進位檔
   今天會被當成文字送進 Monaco。修好窗格會同時修好這一邊，代價是
   **少數今天看得到的檔案會變成看不到** —— 這一句必須進 release note。
3. **每行三組 ANSI 顏色的 log 就會被判為二進位。** 那是 `npm`／`cargo`／`pytest`／
   `go test` 的預設輸出形狀，也是使用者最想在瀏覽器上看的檔案之一。
4. **全檔掃描的成本是 2.66 ms／2 MiB**（vs 窗格版 11.6 µs）。
   ADR 0015 給預覽的預算是 3 秒，所以這是 0.09%。「窗格是為了效能」這個理由不成立。

**還沒量、而且擋著功能 ①：** claude／codex 到底吃不吃相對路徑的圖片
（`08-…md` §4 第 1 項）。這是 `WF-01` 的閘門 —— 不成立的話是設計變更，不是參數調整。

## 這一期最容易做錯的六件事

1. **在 wire 上開一個 `filename` 欄位。** 它看起來只是 UX（讓使用者看到原本的檔名），
   但它是路徑穿越、雙副檔名與覆寫既有檔案這三個問題的**唯一**入口。
   daemon 命名一次消滅三個，而且不需要三段驗證程式碼（D2）。客戶端檔名留在瀏覽器裡當標籤就好。
   —— 但要注意反向的錯誤：**D2 不是通則**。未來的編輯功能必然要讓客戶端指名檔案，
   那需要另一套防護，不是把 D2 搬過去（`01-…md` §1.5）。
2. **相信 `Content-Type`。** 嗅探是判定，宣告是提示。Central 的預檢是為了不佔用節點連線，
   權威判定在 daemon（D3、`03-…md` §3）。
3. **讓 Central 把路徑注入終端機。** 那會開出一條「平台可以對任何 session 打字」的通道，
   而且繞過 single-writer。要的是**前端以 writer 身分打字**（D6）。
4. **把控制字元的門檻從 10% 調到 30% 就算解決了。** 真正的問題是分子是 rune 數、
   分母是位元組數，以及 ESC 被當成控制字元。單位一致之前，任何數字都沒有意義（D14）。
5. **放寬判定而不加 corpus。** 「判得太嚴」的相反不是「判得對」，是「判得太鬆」。
   六個月後會有人為了另一個被擋的檔案再放寬一次，而那時沒有東西會出聲（D16）。
6. **留著「唯讀」這個標示，或反過來把它一次刪光。** 工作區不再唯讀，
   但**預覽**仍然是唯讀的（`FR-FILE-002.AC-01` 沒有改）。
   搜尋 `唯讀`／`read-only` 的每一處命中都要判斷它講的是哪一個（D19、`05-…md` §2.2）。

## 可以只做一半

所以 `06-…md` §6 保留了「部分出貨」這條路徑，不必為了等一個實測而壓著一個已經量清楚的修正。
