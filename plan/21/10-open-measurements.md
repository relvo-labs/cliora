# 10 — 未量測項與待觀察

三類：**開工前必須有答案的一項**、本期新增的三項、以及前期遺留的三項。

## 1. 開工前（**已量，2026-08-14**）

### 1.1 M6 — `git status --porcelain` 在最大的實際 repo 上要多久

**這是 `research/02/10` §5 標成「V2.4 開工前」的唯一一項**，也是本期唯一擋開工的量測。

> ### ✅ 結果（2026-08-14）
>
> **最差 p95 ＝ 279.9 ms**，是設計改動門檻（5 000 ms）的 **1/18**。
> **採集維持「必須完成」，逾時 10 秒（下限值）。**
> 原始資料：`artifacts/dv/local/m6-git-evidence.json`，量測器：`scripts/dv/measure_git_evidence.py`。
>
> | repo | 追蹤檔數 | 狀態 | `status --porcelain` p50/p95 | `diff --stat` p50/p95 | `diff` p50/p95 |
> |---|---:|---|---|---|---|
> | Monstrare | 76 | clean | 2.6 / 3.6 | 1.9 / 2.0 | 1.9 / 2.1 |
> | | | dirty | 2.5 / 4.5 | 2.0 / 2.4 | 2.0 / 2.4 |
> | parksphere | 623 | clean | 11.5 / 12.1 | 9.8 / 10.4 | 9.8 / 10.3 |
> | | | dirty | 11.2 / 12.1 | 11.8 / 12.4 | 12.0 / 12.3 |
> | cliora | 1 358 | clean | 39.4 / 41.0 | 37.1 / 37.5 | 35.6 / 36.0 |
> | | | dirty | 3.2 / 4.4 | 10.4 / 13.3 | 9.6 / 11.9 |
> | kubernetes（淺 clone） | **31 300** | clean | 50.0 / 66.6 | 9.6 / 13.5 | 9.5 / 10.4 |
> | | | dirty | 47.1 / 67.5 | **260.4 / 279.9** | 263.9 / 277.0 |
>
> **三件事值得從這張表讀出來，而它們都不是「數字很小」：**
>
> 1. **貴的不是 `status`，是髒的 `diff`。** 31 300 檔的 repo 上 `status` 只要 67 ms，
>    而同一個 repo 髒了之後 `diff` 是 277 ms——**4 倍**。M6 原本只問 `status`
>    （`research/02/10` §5 的字面），而**只量它會低估這一步的成本 4 倍**：
>    三個命令在同一個採集步驟裡，逾時要對三個一起訂。
>    ⚠️ 這一點是量了才知道的，計畫的「同時量三個」那一句因此不是謹慎而是必要（`01-…md` §2.2）。
> 2. **檔案數不是唯一的變數。** cliora（1 358 檔）的 clean `status` 是 39 ms，
>    而 kubernetes（31 300 檔）是 50 ms——**23 倍的檔案只換來 1.3 倍的時間**。
>    真正的變數是檔案大小分布與 index 的暖度。所以**不要用「我們的 repo 有多少檔」去推估逾時**。
> 3. **cliora 的 clean 比 dirty 慢十倍，那是量測假影不是事實。**
>    clean 那一組緊接在 `git clone` 之後跑，index 的 page cache 是冷的；
>    量測器的一次 warm-up 對第一個 repo-命令組合不夠。
>    **結論不受影響**（最差值來自別的 repo，而且離門檻 18 倍遠），
>    但下一個人重跑時應該預期第一組偏高。

**量測方法的兩個決定**（寫在 `scripts/dv/measure_git_evidence.py` 的 docstring 裡）：

- **在一份丟棄式 clone 上量，不在 repo 本身上量。** 髒的那一半要修改被追蹤的檔案，
  而對一個有人在用的工作目錄做那件事不是量測，是事故。
- **Traqora 不在這台機器上**，所以「medium」用了 `parksphere`，
  「largest」用了 `kubernetes` 的淺 clone——**那不是我們的實際工作負載**，
  它回答的是「上限在哪」而不是「典型值是多少」。

| | |
|---|---|
| **它決定什麼** | evidence 採集的逾時值（`03-…md` §4.3） |
| **為什麼不能事後調** | 訂太短 → 大 repo 上採不到證據，症狀是「證據區塊是空的」，看起來像功能沒做。訂太長（或不訂）→ 一個卡住的 `git status` 讓 run 的最後一步無限期停住，**而租約仍在續**，所以 Central 看到一個永遠在 `finishing` 的 run。**兩種都是新的故障模式，不是一個參數** |
| **怎麼量** | 三種規模 × 10 次 × 乾淨／髒兩種狀態，取 p95。**同時量 `git diff --stat` 與 `git diff`**（三者在同一個採集步驟裡，而 `git diff` 在髒的大 repo 上慢得多） |
| **判準** | 逾時 ＝ p95 × 4，向上取整到 5 秒的倍數，**下限 10 秒**。四倍不是慣例：run 結束時機器上通常還有其他 run 在跑，而磁碟是共用的——**量的時候是 idle，用的時候不是** |
| **會改變設計的門檻** | 最大 repo 的 p95 **> 5 秒** → 採集要從「必須完成」改成「可以失敗」（逾時後照樣送 `run.complete`，那一列標 `collection_timed_out`）。**那是設計改動**，所以要在開工前知道 |

`00-…md` §0.3 的預設值 10 秒**現在成立了，而它是被量出來的不是被沿用的**——
最差 p95 的四倍是 1.1 秒，四捨五入到 5 秒的倍數是 5 秒，而下限 10 秒勝出。
兩條路徑得到同一個數字是巧合，**但差別在於現在有人能回答「為什麼是 10」**。

## 2. 本期新增

### 2.1 M-DV-1 — 驗證命令的實際耗時分布

|---|---|

### 2.1b M-DV-1b — `origin: card` 的佔比（D4 換來的彈性用得多不多）

| | |
|---|---|
| **它決定什麼** | 要不要打開 `require_project_verification`（`06-…md` §2.1 第 4b 項） |

### 2.2 M-DV-2 — PR 建立的失敗率與失敗原因分布

| | |
|---|---|
| **它決定什麼** | ① `pending_pr` 的佇列上限（暫定 50）；② 要不要為某一種失敗做專門的處置 |
| **什麼時候量** | 上線後 30 天 |
| **要看什麼** | 四種失敗的比例。**「同一 head 已有 PR」如果是最大宗，那不是失敗**——它代表 `existing_pr` 的用法比預期常見，而那一格目前走 `delivered`（`04-…md` §5） |
| **不能拿來做什麼** | 這個數字**不進任何自動阻擋邏輯**（D14）。provider 失敗率高不等於要停止派工 |

> ⚠️ **上面那條讀法要加一個限定（2026-08-14 的 `TASK-4` 之後）。**
> 「同一 head 已有 PR」現在有**兩個**觸發者，而它們的意思相反：
>
> | 誰先開了那個 PR | 意思 | 該怎麼反應 |
> |---|---|---|
> | 前一次 run 或人 | `existing_pr` 的正常路徑 | 不是失敗，什麼都不用做 |
> | **這次 run 的 Agent 自己**（路徑 B，`09-…md` §6.1） | `delivery_ref` 指向一份**平台沒有產生的 PR 內文**，而 `04-…md` §3 的保證在這一格靜靜失效 | **這一格會是常態而不是例外**——Agent 可以自己接單開 PR，所以它的佔比其實在量「B 用得多不多」，而那是一個比失敗率更重要的數字 |
>
> 所以**分不出這兩者的話，M-DV-2 的這一格不可讀**——一個健康的數字和一個
> 保證被繞過的數字長得一樣。`09-…md` §6.4 記了最小的做法：
> `evidence(kind=delivery)` 記下「PR 是查到的還是開出來的」。
> **在那個欄位存在之前，這一格只能算「未量測」而不是「量到 0」。**

### 2.2b M-DV-3 — 成功的 run 裡「缺完成證據」的比例　🆕（`TASK-4` 之後新增）

本期原本沒有這一項，而它是**第一次真的派工就撞到的東西**（`09-…md` §6.2）：
run 成功、工作做完、報告寫得比要求更清楚，**而卡片缺兩項完成證據**。

| | |
|---|---|
| **它決定什麼** | 「證據入口在不在 Agent 的順手路徑上」是不是一個真問題，還是 `TASK-4` 的一次意外 |
| **什麼時候量** | 從第一張交付型卡開始，**不用等 30 天**——分母小的時候這個比例最有資訊 |
| **要看什麼** | 成功結束的 run 裡，① `verification_reports` 是空的比例；② `delivery ∈ {pull_request, existing_pr}` 而 `delivery_ref` 是空的比例。**兩個分開看**：①是 Agent 沒提交，②可能是平台沒開成（`04-…md` §5 的四種失敗之一），成因不同 |
| **判準** | ①**超過 20% 就不是 Agent 的問題，是入口的問題**。派工指示、CLI 的順手程度、run 結束時的提醒，三者選一個改。②**只要走路徑 B（Agent 自己開 PR，`09-…md` §6.1）就是 100%**，所以這一格不是分布而是一個開關：**B 有沒有證據入口** |
| **附帶要看的** | 這些卡最後**怎麼進 done 的**。如果多數走 `--force`，那 `--force` 的次數就不再是判準訊號而是噪音——它同時混進了兩種完全不同的原因（判準訂錯 vs 證據沒進得來），而 §2.3 那一列讀的是前者 |
| **不能拿來做什麼** | 不拿它去放寬 Done Gate 的六項。**缺證據就是缺證據**——要改的是證據怎麼進來 |

### 3.1 M-SC-2 的量測方法（V2.3 已改寫，本期沿用）

`plan/20/08` §3 第 3 條記過：兩次 idle 基線的 p95 相差 27%，而判準是 20%——
整個判準落在雜訊底下。改成：

> **同一輪連續量三次取 p50 的中位數，並且在「有 run 在跑」與「沒有 run」
> 兩種情況下各量三次**，比較的是那兩組的中位數。

本期的基線擷取（`01-…md` §1）已經照這個方法做。
