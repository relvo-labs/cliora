# Release note — V2.2 Agent Runner

Design decisions: [ADR 0029](adr/0029-v22-agent-runner-model-and-run-lifecycle.md),
[ADR 0030](adr/0030-v22-run-log-and-card-artifacts.md),
[ADR 0031](adr/0031-v22-isolated-run-directory-and-git-fetch.md).
Security review: [docs/security-review-v22.md](security-review-v22.md).

## What this adds

A Developer presses **Dispatch to Agent** on a card in the Ready lane. A runner on an
enrolled node claims it, clones the project's registered repository into a directory the
daemon owns, runs `claude` or `codex` there with nobody watching, streams the log back,
talks to the card, and attaches its output as artifacts.

Kill the runner process and the lease expires: the card is re-queued and a second runner
finishes it. **Nothing touches anyone's workspace** — the agent works in its own clone,
and `git status --porcelain` in the user's directories stays empty throughout.

## Turning it on

Two flags, and the second is inside the first:

```
CLIORA_PROJECTS_ENABLED=true
CLIORA_AGENT_RUNS_ENABLED=true
CLIORA_GIT_ALLOWED_HOSTS='["github.com"]'   # empty allows nothing, by design
```

Released as `agentd` **0.9.0** (`daemon/VERSION`, cut 2026-08-13 — the code landed
with this phase, the version number was cut later, at the start of V2.3's `SC-00`).

On a node, `agentd` **0.9.0** or newer, plus:

```yaml
runner:
  enabled: true            # absent means off: an upgrade does not start running work
  git:
    allowed_hosts: ["github.com"]
```

**`git` is a new prerequisite** for runner mode. `agentd doctor` reports it, along with
the run-root isolation check and whether each CLI can be driven non-interactively.

## Four things worth knowing before you switch it on

**1. A runner node should be dedicated.** V2.2's authorization boundary is *enrollment*:
any enrolled node's runner can claim any project's card and pull any project's code, and
an agent inside the sandbox may use that machine's existing git credentials for anything
git can do — **including push**. That is deliberate rather than a gap; what the platform
provides is observability, not prevention. Every run reports its remotes (with any
userinfo masked) and how many commits it left unpushed.

The Agents page shows **⚠ mixed use** for a node that also serves interactive sessions,
because an agent running there can read those directories. The platform does not prevent
that and says so.

**2. Token spend is measured, not capped.** This is the phase's one knowingly
unmitigated risk. `claude` has `--max-budget-usd` and `codex` has no equivalent, and
wiring half of it would suggest a protection only one path has. A card-level budget
arrives in V2.3.

**3. A run's log is a diagnostic, an artifact is a deliverable**, and they have
different lifetimes on purpose. Logs expire (3 days on success, 14 on failure) and are
truncated from the middle at 5 MB with the dropped byte count stated. Artifacts follow
the card and are never deleted on a timer — so a project accumulates them until somebody
decides which to remove.

**A crash of Central loses each in-flight run's last ≤64 KiB of log.** That is accepted:
a log can be regenerated by re-running, and the two things that cannot — artifacts and
card messages — deliberately do not travel that path.

**4. An artifact is always a download.** There is no setting that renders one: Cliora is
a single-origin deployment, so "open in a new tab" and "render inline" are the same act.
Images, plain text and markdown can be previewed; markdown is shown as plain text.

## What has not changed

- **Interactive sessions.** No run writes a `terminal_sessions` row, uses the terminal
  relay, holds a writer slot or creates a tmux. With both flags off the system behaves
  exactly as V2.1 did.
- **The platform issues no `git push`.** Not once, anywhere, in this version.
- **No automatic assignment.** Claiming is the runner's action; dispatch queues a card
  and returns.
- **A card's review gates still require a human.** An agent's output is not an approval,
  and a run credential cannot reach that endpoint at all.

## Upgrading a fleet

Nothing here forces a fleet-wide update. A node on 0.8.0 keeps serving interactive
sessions and is simply never offered a run; the console says which version it would
need. `node_update`'s staged rollout is unchanged and is not triggered by this release.

## Known limits

| Limit | Why |
|---|---|
| Any enrolled node may fetch any project's code | No project↔agent binding until V2.3 |
| No secrets | A card that declares `required_secrets` is refused at dispatch, with the version it starts working in |
| Only `delivery: none` and `artifact` | Branches and pull requests arrive with the platform's own git write path |
| Labels are shown, not matched | Label matching is a later feature; the console labels the field accordingly |
| No token budget | Measured this phase (M-AR-10), capped in V2.3 |
