# V2.4 — 交付、驗證與完成判準

`agentd` **0.11.0**／contract **v1.13.0**／migration **0038**／ADR **0033**。
受 `CLIORA_AGENT_RUNS_ENABLED` 控制；旗標關閉時行為與 V2.3 一致。

## 可以做什麼了

**成果有五種離開的方式**，而不再只有「有沒有推分支」：不交付、以產物交付、以分支交付、
以合併請求交付、接續既有的合併請求。**平台會替你開 PR**——內文含目標、逐項驗收結果、
驗證摘要與 run 連結，由平台產生而不是由 Agent 產生，因為讀它的人沒有本平台的帳號。

**驗證命令由平台執行，結束碼是真的。** 命令來自兩個地方：專案設定與卡片自己的清單。
報告上兩者都標「機器驗證」，並各自標明是誰指定的。

**卡片進入「完成」現在會被檢查**（見下，這是最有感的一條）。
執行計畫、驗證報告與證據三份紀錄出現在卡片上，每一列都標明它是
「Agent 自述」「平台觀測」還是「機器驗證」。

**專案可以覆寫流程定義**（只能停用既有項目），**跨專案儀表板多了一組交付指標**。

## 行為改變

**① 拖到「完成」會被檢查。** 六項：完成摘要、每一項驗收標準都有結果、驗證報告、
沒有未處理的重大失敗、相依卡片皆已完成、以及依交付方式應有的證據。
缺項時**逐項指名**，不是只回一句話。卡片詳情頁**平時就顯示**這六項，
所以你在拖之前就看得到缺什麼。

管理者可以帶著理由強制推進（需要新的 `task.force_done` 權限）。
**那個理由會永久顯示在卡片上**，而且沒有任何操作可以單獨清掉它——
唯一的方式是把卡片移出「完成」再正常推進一次。

⚠️ **兩個不會被擋的情況**，都是刻意的：只開看板沒開 Agent 執行的部署完全不受影響；
從來沒有派工過的卡片不會被要求交付證據（`delivery` 的預設值是「合併請求」，
而一張手動管理的卡永遠不會有 PR）。

**② 驗收標準的結果收緊成四個值**（`passed`／`failed`／`partial`／`not_verified`）。
升級時**不認得的舊值一律轉為 `not_verified`**，並印出被轉換的筆數。
在那之前這個欄位是自由字串，所以「每一項都有結果」這句檢查對任何文字都會通過。

**③ `delivery: pull_request` 與 `existing_pr` 不再被拒絕**，但改成對**這張卡自己的宣告**
提出更具體的拒絕：沒有來源、沒有目標分支、主機沒有整合、分支不在命名空間內。

**④ 新增兩個 Admin 權限**：`process.manage`、`task.force_done`。
既有 25 個權限的角色歸屬不變。

## 已知的取捨

**`existing_pr` 只能接續平台自己開的 PR。** 平台只推得到 `cliora/` 命名空間之內
（那條約束編譯在節點程式裡，V2.3 通過安全審查），而別人手動開的 PR 的來源分支不在裡面。
**這看起來像缺陷，實際上是邊界**——要接續別人的分支，請改用 `delivery: branch` 並自行合併。

**GitLab 尚未支援**，且在**派工當下**就拒絕，不會等到工作做完才失敗。

**PR 的作者是憑證的擁有者，不是按下派工鍵的人。** PR 內文的最後一行會寫出這件事，
因為讀到它的人沒有辦法從別處查。

**平台永不自動合併、永不核可自己開的 PR、永不關閉他人的 PR、永不動標籤。**
這四件事以「動作表裡沒有那個字」的形式成立，兩個 gate 在守。

**合併請求建立失敗不會讓執行失敗。** 分支已經推上去、工作還在，
結果標為「僅交付分支」，可以手動開 PR，而卡片不會因為缺 PR 被擋住。

**逾時不重試。** 建立不是冪等操作：一次「請求送到了、回應沒回來」的逾時如果重試，
會在別人的儲存庫上開出第二個 PR。

## 升級注意

**一定要做的：**

- `alembic upgrade head`（`0035`–`0038`）。**`0036` 會改寫既有的驗收標準結果**，
  並在輸出印出改了幾筆；`downgrade` 不會還原那一步。
- 要用合併請求交付的專案，需要一枚 `kind: provider_token` 的機密，
  權限**只要 `pull request: write`**，並在儲存庫設定上指定它。
  **記下它屬於誰**——每一個平台開的 PR 都會顯示那個身分。

**可以晚點做的：**

- `agentd` **0.11.0** 的發布時機。出口條件全綠不代表要推給所有 node。
  0.10.0 的 node 連上來仍能正常領取與完成 `none`／`artifact`／`branch` 三種卡，
  只是不跑驗證命令——因為本期的 contract 新增**全部**在 node→central 方向。
- `CLIORA_PROVIDER_API_HOSTS` 預設只有 `api.github.com`，多數部署不必動它。
- 專案的驗證命令與 `require_project_verification`（**預設關閉**）。

⚠️ **停在 `agentd` 0.8.0 的 node 需要升級。** 那些節點會靜默丟棄任何需要交付的卡片
（`spec.branch` 是 v1.12.0 加的，而它們的解碼器拒絕未知欄位且不回應）。
本期起 Central 不會再把交付型卡片派給它們，並在 Agents 頁說明原因——
但那是止血，不是修好：**升級它們**。
